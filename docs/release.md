# Releasing pbrain

pbrain ships as a Claude Code plugin. A release is: bump the version, cut the
changelog, generate the "what's new" page, tag, and publish a GitHub release.
`scripts/release.sh` does all of it reproducibly — **dry-run by default**, only
writing when you pass `--apply`, and idempotent so a half-finished release is
safe to resume.

## The two version files

pbrain carries two version files that must never drift:

| File | Format | Who reads it |
|---|---|---|
| `VERSION` | `x.y.z.0` (four-part) | humans, scripts |
| `.claude-plugin/plugin.json` | `x.y.z` (SemVer) | `lib/update-check.sh`, the plugin host |

`scripts/release.sh` is the **sole writer** of both, so a bump always touches
them in lockstep. Don't hand-edit either — run the script.

## One-shot: cut a release

```bash
# See what would happen (writes nothing):
scripts/release.sh cut minor

# Do it:
scripts/release.sh cut minor --apply
```

`cut <major|minor|patch> --apply` runs, in order:

1. **bump** — `VERSION` + `plugin.json` to the next version.
2. **changelog** — roll `## [Unreleased]` into `## [x.y.z] — <today>`, leaving a
   fresh empty `[Unreleased]` on top.
3. **whats-new** — generate `docs/whats-new/<x.y.z>.html` from that version's
   changelog section.

Then review the diff, commit it (on a branch, open a PR, merge), and finish:

```bash
scripts/release.sh tag --apply       # create + push the vX.Y.Z git tag
scripts/release.sh publish --apply   # gh release create, notes from the CHANGELOG
```

`tag` and `publish` are split out from `cut` on purpose: you tag the **merge
commit**, not the PR branch.

## Individual steps

| Command | What it does |
|---|---|
| `release.sh current` | print the current version (`x.y.z`) |
| `release.sh next <level>` | print what the next version would be |
| `release.sh bump <level> [--apply]` | write both version files |
| `release.sh changelog [--version V] [--apply]` | cut `[Unreleased]` → `[V]` |
| `release.sh whats-new [--version V] [--apply]` | regenerate the what's-new HTML |
| `release.sh tag [--version V] [--apply]` | create + push `vV` |
| `release.sh publish [--version V] [--apply]` | `gh release create vV` |

Env: `PBRAIN_RELEASE_DATE=YYYY-MM-DD` overrides the changelog date;
`PBRAIN_RELEASE_REMOTE` overrides the push remote (default `origin`).

## What's new on update (PB-129)

`docs/whats-new/<version>.html` is a self-contained, styled page — a
marketing-style guide, not a changelog dump: a hero, per-feature sections that
say what you can now do, and "try it" command cards that show the feature in
action.

### Author the guide (`docs/whats-new/<version>.md`)

For a real release, write a short highlights file and the renderer turns it into
the page. The renderer (`lib/whats-new-render.py`) understands:

```markdown
# Hero headline                ← the big <h1>
> One-line tagline.            ← the lede under it

## Feature name                ← a feature section
Prose with **bold**, `code`, [links](https://…).
- optional bullets

​```flow                        ← a connected-chip pipeline diagram
plan -> implement -> test -> ship -> land
​```

​```bash                        ← a fenced block becomes a "Try it" command card
/some-command --flag
​```

| Command | What changed | Try |   ← a scannable coverage table
|---|---|---|
| `/x` | does y | `cmd` |
```

Lean on the **table** for breadth (cover every changed command at a glance) and
the **flow** + **try-it cards** for the headline features. The goal is a guide a
user can skim in 20 seconds, not a wall of prose.

Keep it to a few features, lead with the user-visible win, and put a runnable
command in each "try it" block. If no `<version>.md` exists, the pipeline falls
back to rendering the version's **changelog section** so a release always
produces a page — just a plainer one.

Both shapes are generated by `lib/whats-new.sh render` (sourced by
`scripts/release.sh whats-new` / `cut`).

`lib/whats-new.sh check`, sourced from `lib/vault.sh` on every command run,
tracks the last local plugin version in a small state file
(`$XDG_STATE_HOME/pbrain/whats-new.seen`). When the local version **advances**
(a `/plugin update` landed) and a matching doc exists, it prints a one-line
`✨ What's new …` pointer and, on macOS, opens the page — **once** per upgrade,
then stays quiet. A fresh install just records a baseline (no pop). The whole
path is best-effort and never fatal, and is skipped on dev installs
(`$PBRAIN_DEV_DIR` set), where the version legitimately runs ahead of `main`.

## Authoring changelog entries

Write entries under `## [Unreleased]` as you land work, using the
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/) sections (`### Added`,
`### Changed`, `### Fixed`, …). The what's-new renderer understands a small
markdown subset — `### headings`, `-` bullets, `**bold**`, `` `code` ``, and
`[text](url)` links — so keep entries within that and they'll render cleanly.

## Tests

`tests/release.bats` covers the bump math, version-file lockstep, changelog cut
+ idempotency, what's-new generation, and the surface-once state machine. Run:

```bash
bats tests/release.bats
```
