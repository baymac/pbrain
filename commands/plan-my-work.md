Run this with your shell first (substituting any argument for `$ARGUMENTS`), then follow the INSTRUCTIONS in the token it prints:

```bash
bash "${PBRAIN_DEV_DIR:-${CLAUDE_PLUGIN_ROOT:-$HOME/.claude/plugins/marketplaces/pbrain}}/commands/plan-my-work.sh" $ARGUMENTS
```

`/plan-my-work` is the **execution layer** of the daily loop. It runs **ONE issue at a time** through the auto-execution pipeline. **PB-94 stripped it down:** it no longer plans the day — there is no `## Work tracker`, no project picking, no plans-profile, no `task add|remove|list`. **State lives in Plane only**: the loop reads issue state via `/project-manager spec <id> --read` and writes status/log back via `/project-manager move|comment`. This command **writes nothing to the vault**. Task *selection* is groom's job (`/project-manager groom` feeds ids here one at a time).

**The 5-stage pipeline.** Each stage checks the issue's own `auto:<stage>` label (from `auto_gates` in `spec --read`). Present → the stage **auto-advances** (announced); absent → it is a **manual gate** and, with no go, the loop **parks** there. Stages, in order: **plan** (`auto:plan` — worktree + draft plan + save it to the issue) → **implement** (`auto:implement` — code + local commit) → **test** (`auto:test` — run tests, capture results) → **ship** (`auto:ship` — push + open PR) → **land** (`auto:land` — docs + merge, **no release**). Semantics are **independent, stop-at-first-gap**: a label clears only its own stage, and a later label does not imply an earlier one. An issue with no `auto:*` labels is fully manual (the safe default). **Invariant:** even with `auto:land`, a red CI **hard-stops** the merge — `auto:land` waives only the typed-confirm half, never CI-green, and land never cuts a release.

The script prints one of:

- `PLAN_MY_WORK_EXECUTE` — the loop. The data block carries `target_ref` + `target_kind` (id | desc), the per-project **working locations** (`plane.json` `projects[].work`, set via `/project-manager workdir`), the project registry, and `${PM_CMD}`/`plane_web_base`. The instructions live in `commands/templates/plan-my-work/execute.txt`. Flow: **pre-flight** — `spec <id> --read` for state + dependencies; if `blocked_by` is non-empty, drive the **blocker(s) first** (iteration 1…N) then the issue; if the id is a **parent with open sub-issues** (`/project-manager subtree`), drive **each child** as its own iteration (one branch/PR/merge each), closing the parent last (PB-81). Then run the **5 stages** for the leaf, **parking** (WIP-commit + push + a `pbrain park:` breadcrumb comment) at the first stage without its label so a later run **re-attaches** to the pushed branch and resumes. Each stage appends a **live summarized log** comment to the issue (plan, files changed, test results, PR link). `move→doing` at the start, `move→done` after land. This is the only pbrain command that touches code/branches/PRs/merges — work happens in a configured repo on an isolated worktree/branch; the only irreversible step (merge) is gated on CI-green + `auto:land`-or-typed-confirm. `gh`/CI absent → push + hand back a manual URL, never fabricate a PR/merge.
- `PLAN_MY_WORK_NEEDS_ID` — no id was given (and none resolvable). pmw runs ONE issue and needs to know which — ask the user for a Plane id (`PB-96`) or a description (searched/filed via `/project-manager`). It does **not** pick tasks itself: selection + ordering is groom's job (`/project-manager groom` feeds ids here one at a time).
- `PLAN_MY_WORK_NO_PLANE` — Plane isn't configured, and the loop reads/writes all state in Plane. Tell the user to set it up with `/project-manager`, then re-run `/plan-my-work <id>`.

**Natural-language form (PB-96).** You don't have to type a bare id. A plain-words request is normalized by the `.sh` into the same execute path: a **PB-ref** (`pb96` / `96`, alone or after a verb like `work on pb96`) → resolved straight against Plane (`target_kind=id`); a **free-text description** after an action verb (`fix the routing bug`) → the **find-or-file cycle** (`target_kind=desc`): search Plane for a matching issue, and if none matches, file a NEW one via `/project-manager file "<desc>"`, then execute the resulting id. A bare verb with only filler (`do some work`) names no task → `PLAN_MY_WORK_NEEDS_ID`. `task execute <id>` remains as a back-compat alias for `<id>`.
