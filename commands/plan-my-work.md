Run this with your shell first (substituting any argument for `$ARGUMENTS`), then follow the INSTRUCTIONS in the token it prints:

```bash
bash "${PBRAIN_DEV_DIR:-${CLAUDE_PLUGIN_ROOT:-$HOME/.claude/plugins/marketplaces/pbrain}}/commands/plan-my-work.sh" $ARGUMENTS
```

`/plan-my-work` is the **execution layer** of the daily loop. It runs issues through the auto-execution pipeline. **PB-94 stripped it down:** it no longer plans the day — there is no `## Work tracker`, no project picking, no plans-profile, no `task add|remove|list`. **State lives in Plane only**: the loop reads issue state via `/project-manager spec <id> --read` and writes status/log back via `/project-manager move|comment`. This command **writes nothing to the vault**. Task *selection + ranking* is groom's job (`/project-manager groom` builds the cross-project queue); pmw only **consumes** it.

**The 4 execution modes (PB-147).** The execution loop is **identical in all four** — they differ only in how an issue is **selected** and how the run is **gated**:

1. **By id** — `/plan-my-work PB-96` (or `96`, or `work on pb96`). Runs the 5 stages on that one issue.
2. **Fix an issue** — `/plan-my-work fix the routing bug` (a description, not an id). Runs the **find-or-file** cycle: search Plane → confirm the match → if none, hand to `/project-manager file "<desc>"` (full triage: checks sub-issue / relates-to / blocked-by links) → execute the resulting id.
3. **Auto-drive the queue** — `/plan-my-work auto`. **Hands-off**: claims the top of groom's **cross-project** queue, runs the 5 stages, and at any manual gate it can't satisfy (notably **land** — groom never grants `auto:land`) it **parks + logs a bottleneck + moves on** to the next issue, looping until the queue is empty, then reports a roll-up. Never auto-merges.
4. **Top of queue** — `/plan-my-work` (no arg) or `/plan-my-work top`/`next`. Claims the **single** top issue, runs it, then **offers** to go to the next (a manual gate between items — it does not auto-continue).

Modes 3 & 4 consume the **Queued state** (groom's ranked, blockers-first, cross-project queue), which **excludes `parked` issues** — a human adds the `parked` label to hold an issue off the hands-off modes. An **explicit id** run on a parked issue still runs (a human named it) with a one-line warning. The merge invariant is unchanged: nothing auto-merges; hands-off auto-drive parks at the land gate.

**SRP mid-loop triage (PB-153).** When a discovery surfaces mid-loop — the user says something, or pmw finds a bug/problem — pmw triages it instead of silently growing the current PR: **SRP-first**, it defaults to filing a **separate** issue (`/project-manager file`), only folding in when it's the same single responsibility (or updating the existing issue for a trivial delta); it **always captures** it; and it sets the current issue **`blocked_by`** the new one when it blocks finishing the current PR, else just **`relates_to`**. Each PR stays scoped to one thing.

**The 5-stage pipeline.** Each stage checks the issue's own `auto:<stage>` label (from `auto_gates` in `spec --read`). Present → the stage **auto-advances** (announced); absent → it is a **manual gate** and, with no go, the loop **parks** there. Stages, in order: **plan** (`auto:plan` — worktree + draft plan + save it to the issue) → **implement** (`auto:implement` — code + local commit) → **test** (`auto:test` — run tests, capture results) → **ship** (`auto:ship` — push + open PR) → **land** (`auto:land` — docs + merge, **no release**). Semantics are **independent, stop-at-first-gap**: a label clears only its own stage, and a later label does not imply an earlier one. An issue with no `auto:*` labels is fully manual (the safe default). **Invariant:** even with `auto:land`, a red CI **hard-stops** the merge — `auto:land` waives only the typed-confirm half, never CI-green, and land never cuts a release.

The script prints one of (each carries a `mode:` line — 1 | 2 | 3 | 4 — so the instructions branch deterministically):

- `PLAN_MY_WORK_AUTODRIVE` (mode 3) — hands-off auto-drive. The block carries a `session` token, working locations, the registry, and `${PM_CMD}`/`plane_web_base`. The instructions (`MODE 3 — AUTO-DRIVE LOOP` in `execute.txt`) loop: `claim-next --session <token>` (cross-project, parked-skipped) → run the 5 stages → park+log+move-on at any unmet gate → repeat until `null`, then roll up.
- `PLAN_MY_WORK_QUEUE_PULL` (mode 4) — the single top of the queue was atomically **claimed** for this session (→ Planning) and named; the loop runs it once, then offers the next. Parallel sessions claim different issues.
- `PLAN_MY_WORK_EXECUTE` — the loop (mode 1 by id, mode 2 by desc). The data block carries `target_ref` + `target_kind` (id | desc), the per-project **working locations** (`plane.json` `projects[].work`, set via `/project-manager workdir`), the project registry, and `${PM_CMD}`/`plane_web_base`. The instructions live in `commands/templates/plan-my-work/execute.txt`. Flow: **pre-flight** — `spec <id> --read` for state + dependencies; if `blocked_by` is non-empty, drive the **blocker(s) first** (iteration 1…N) then the issue; if the id is a **parent with open sub-issues** (`/project-manager subtree`), drive **each child** as its own iteration (one branch/PR/merge each), closing the parent last (PB-81). Then run the **5 stages** for the leaf, **parking** (WIP-commit + push + a `pbrain park:` breadcrumb comment) at the first stage without its label so a later run **re-attaches** to the pushed branch and resumes. Each stage appends a **live summarized log** comment to the issue (plan, files changed, test results, PR link). `move→doing` at the start, `move→done` after land. This is the only pbrain command that touches code/branches/PRs/merges — work happens in a configured repo on an isolated worktree/branch; the only irreversible step (merge) is gated on CI-green + `auto:land`-or-typed-confirm. `gh`/CI absent → push + hand back a manual URL, never fabricate a PR/merge.
- `PLAN_MY_WORK_NEEDS_ID` — the **Queued state is empty** (mode 4 / no-arg had nothing to claim) and no id/description was given. Ask the user for a Plane id (`PB-96`) or a description (searched/filed via `/project-manager`), or suggest `/project-manager groom` to (re)build the queue. pmw does **not** pick or reorder tasks itself — selection + ranking is groom's job.
- `PLAN_MY_WORK_NO_PLANE` — Plane isn't configured, and the loop reads/writes all state in Plane. Tell the user to set it up with `/project-manager`, then re-run `/plan-my-work <id>`.

**Natural-language form (PB-96).** You don't have to type a bare id. A plain-words request is normalized by the `.sh` into the same execute path: a **PB-ref** (`pb96` / `96`, alone or after a verb like `work on pb96`) → resolved straight against Plane (`target_kind=id`); a **free-text description** after an action verb (`fix the routing bug`) → the **find-or-file cycle** (`target_kind=desc`): search Plane for a matching issue, and if none matches, file a NEW one via `/project-manager file "<desc>"`, then execute the resulting id. A bare verb with only filler (`do some work`) names no task → falls through to the queue (mode 4). The explicit mode selectors `auto`/`drive` (mode 3) and `top`/`next` (mode 4) are consumed before NL routing. `task execute <id>` remains as a back-compat alias for `<id>`.
