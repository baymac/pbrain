Run this with your shell first (substituting any argument for `$ARGUMENTS`), then follow the INSTRUCTIONS in the token it prints:

```bash
bash "${PBRAIN_DEV_DIR:-${CLAUDE_PLUGIN_ROOT:-$HOME/.claude/plugins/marketplaces/pbrain}}/commands/plan-my-work.sh" $ARGUMENTS
```

This is the **work layer** of the daily loop. `/plan-my-day` builds the day's *shape* — life anchors (calendar, fitness, meals, walk, bed, habit reminders) and empty work **blocks** for focus time. **PB-85:** `/plan-my-work` no longer fills those blocks — it owns a **standalone `## Work tracker`**, a flat CEO-overview ledger that lives below the day's shape and is **decoupled** from the glance work-blocks. The tracker records what got done, notes, time taken, and links — the project brain (one pbrain project = one Plane PROJECT; see `/project-manager`). Weekly/monthly goals are a CEO overview — which projects are in play, at what priority, and at what **% allocation** (summing to 100) — not task text. The tasks live in Plane.

**Autonomy (PB-85):** `/plan-my-work` never tells you to run `/plan-my-day` (or `/journal`/`/gratitude`) first. If today has no daily-planning file, it scaffolds a minimal one (frontmatter + empty `## Work tracker` + `## How it went`) and proceeds. If `/plan-my-day` also ran, its `## Today at a glance` sits **above** the tracker and is left untouched.

The script prints one of:

- `PLAN_MY_WORK_SESSION` — the main flow. The data block carries the plans profile's **working_style + day shape** (to gauge how much fits, not to build blocks), this week's project goals (`allocation_percent`/`plane_project`), the registry, a `progress_json`, this week's `## Work tracker` rows, `glance_present` (whether `/plan-my-day` laid a glance above the tracker), and today's file. The instructions live in `commands/templates/plan-my-work/session.txt` (the `.sh` is a thin dispatcher). Steps: **(1)** preflight (the file exists, scaffolded if needed), **(2)** READY-CHECK — **delegate grooming to `/project-manager`** (`PBRAIN_PM_CALLER=plan-my-work bash <pm> review --projects …`); PM owns the enrichment/triage, **(3)** progress report (per-goal alloc% · Plane pct · tasks done · flags; **% of week's importance met = Σ(alloc%·pct)/Σ(alloc%)**; one-line monthly read), **(4)** pick today's projects, **(5)** pull ready tasks into an **ordered ledger** (biggest-rock-first; approved tasks first within a priority), **(6)** write the standalone `## Work tracker` (never touch the glance), **(7)** confirm tightly.
- `PLAN_MY_WORK_NO_PROFILE` — there's no committed plans profile yet, so there's no working style to gauge the day's capacity against. The plans profile is the working-style source — tell the user to run `/plan-my-day` once to create it (it builds the profile), then come back. Don't proceed. (This is the *only* command pmw still can't run without; everything else is autonomous.)
- `PLAN_MY_WORK_TASK` — `task add|remove|list` on today. Revise the standalone **`## Work tracker`** (rows pulled from Plane, with the full tie in the `Plane id` column) — one row per task, no glance re-flow, life anchors untouched (PB-85). Follow the per-action INSTRUCTIONS. For a brand-new task, offer to create it in Plane (via `/project-manager`) before pulling it. If today has no file yet, pmw scaffolds one first (no nudge).
- `PLAN_MY_WORK_EXECUTE` — `task execute [PB-id]`: **drive the work-tracker ledger to Done**, one task at a time, through the full lifecycle (pick → in-progress → **spec/approval gate** → implement → finish → PR → **gated merge** → done), then **cascade** (next ledger row → pull more ready tasks → new project). **PB-85:** there is no "current block" — the `.sh` emits `NEXT TASKS`, the not-done ledger rows in order (the optional `PB-id` arg moves that row to the **front**), so a re-run resumes the first unfinished task. It surfaces the per-project **working locations** (`plane.json` `projects[].work`, set via `/project-manager workdir`). **Parallel execution (PB-85):** each session drives its OWN task in its OWN worktree — there is NO "one task in-progress at a time" rule, and other in-progress rows / other worktrees are ignored, not resumed or cleaned up. **Spec/approval gate (PB-45):** execute reads the issue's recorded plan + approval (`/project-manager spec "<tie>" --read`) — an **approved** plan FAST-PATHS straight to implement; an **unapproved** one FALLS BACK to drafting inline with a [GATE], then offers to save it as approved. **Parent target (PB-81):** when the targeted ref names an issue that has open sub-issues, execute resolves it with `/project-manager subtree "<ref>"` and treats the parent as ONE logical target executed as SEPARATE SEQUENTIAL UNITS — it pulls each open child into the ledger and drives them in priority → due → id order, one branch/PR/double-gated-merge per child, then closes the parent only after the last child merges. A childless issue (or a parent whose children all landed) is driven as a single unit. Targeting a parent no longer fans out uncontrollably. The lifecycle, git/PR/merge mechanics, Plane writes (routed through `/project-manager`, the sole Plane writer), and the cascade live in `commands/templates/plan-my-work/execute.txt`. This is the only pbrain command that touches code, branches, PRs, and merges: work happens in a configured pre-existing repo/workspace on an isolated worktree/branch, and the only irreversible step (merge) is **double-gated** — CI green (or explicit waive) **and** a typed `merge <PB-id>` confirm. `gh`/CI absent → push + hand back a manual URL, never fabricate a PR/merge. **Natural-language routing (PB-96):** you don't have to type `task execute` — a plain-words work request (`fix the X bug`, `work on PB-96`, `do some work`, or just `pb96`) is normalized by the `.sh` into the canonical `task execute [PB-id]` form and runs this same lifecycle, NOT the triage/grooming path. A leading action verb (fix/do/work/implement/build/ship/finish/start/tackle/…) or a bare PB-ref token triggers it; any PB-ref in the request becomes the target, and a verb with no ref drives the ledger / cascades. `/plan-my-work` with no args (or the planning form) still lays out the day's work (SESSION) untouched.

The **`## Work tracker`** schema — a standalone CEO ledger (PB-85: NO Block column; `/end-of-day` reconciles it back to Plane by the `Plane id` tie, in both directions):

```
| Task | Project | Plane id | Priority | Est | Status | Started | Done at | Time taken | % complete | Links | Notes |
|---|---|---|---|---|---|---|---|---|---|---|---|
| ship allocation refactor | Lettuce | <pid>:<iid> | high | 2h | planned | | | | | | |
```

`Started`/`Done at`/`Time taken` capture how long work actually took; `Links` holds PR/issue/doc links a CEO would want at a glance. The "Work the plan" and "Deep work" habits score against this table at `/end-of-day`. Old daily files with a `Block` column still read fine — the parser keys off header names, so no migration is needed.

`task execute` authors the `Status` column **live mid-day** — `in-progress` when a task starts (with `Started`), `done` (with `Done at` + `Time taken` + `% complete` = 100) only after its PR merges. The `Status` column *is* the lifecycle state, so it's resume-safe: `/end-of-day` maps `in-progress → doing` idempotently, and a re-run of `task execute` skips `done` rows and resumes an `in-progress` row (with a PR link in `Links`) at the merge gate.
