Run this with your shell first (substituting any argument for `$ARGUMENTS`), then follow the INSTRUCTIONS below based on the token it prints:

```bash
bash "${PBRAIN_DEV_DIR:-${CLAUDE_PLUGIN_ROOT:-$HOME/.claude/plugins/marketplaces/pbrain}}/commands/project-manager.sh" "$ARGUMENTS"
```

`/project-manager` is the operator between pbrain and **Plane** (makeplane). Plane owns the task tree (Module → Issue → Sub-issue) and the UI; pbrain reads ready work and writes status back through two seams. One pbrain "project" = one Plane PROJECT; a workspace holds many, tracked in a small registry (`projects [--sync]`). **Plane is pbrain's sole project backend** — task planning and project progress require it. When Plane isn't configured the ops emit `PM_NOT_CONFIGURED` (a friendly "set Plane up" note); the setup family still runs.

**Never print or echo the Plane API token back to the user — treat it as a secret at every step.**

## Driving Plane in plain words (the main path)

The user mostly won't type verbs — they'll say what they want. **Any first word that isn't a known verb is treated as a natural-language instruction and routed.** You can also force it with `route <words>`. The script prints `PM_ROUTE` + a compact **capability catalogue** + (on a direct invocation) the user's daily/weekly/monthly plan context so your routing is goal-aware. Then you:

1. **Resolve** the issue(s) with `find "<link | PB-26 | name fragment>"` → candidate cards `{tie, id, title, state, project}`. One → use its `tie`; several → ask which; zero → offer to create.
2. **Map** the instruction to specific verbs (one ask can be several ops; batch with `update --edits`).
3. **Confirm only when it matters** — irreversible ops, ambiguous targets, or creating a person/project. Routine edits just apply.
4. **Execute** and report one tight line per issue; relay any `PLANE_ERROR`.

**The write catalogue** (each is a verb; `update --edits '[{tie,field,value}]'` does any of them, batched): `find` · `move` · `priority` · `timeline` · `tag/untag/labels` · `assign` (by name/email/uuid) · `comment` · `reparent` · `cycle` · `module` · `issue` · `project-create` · `description`/`title`/`start_date` · `relation:<type>` · `subissue` · `link`. Listers `labels|members|cycles|modules` give the name→uuid tables. To break ONE issue down interactively, `explode <ref>` runs a Socratic walk (see `PM_EXPLODE`). To draft + approve ONE issue's implementation plan ahead of execution, `spec <ref>` runs a Socratic walk (see `PM_SPEC`) — the spec/approval gate (PB-45). To FILE new work from a rough dump, `file "<dump>"` (aliases `create`/`track`/`capture`) explodes it into a triage-ready item of ANY type and creates it (see `PM_FILE`, PB-67) — `--fast` infers + one-confirm, the default runs the full Socratic build-up. `labels --seed [--projects R,…]` backfills the convention labels (`bug`/`feature`/`chore`/`docs`), the `plan-approved` seam, the 5-stage `auto:*` execution labels (`auto:plan`/`auto:implement`/`auto:test`/`auto:ship`/`auto:land`, PB-94 — the `/plan-my-work` pipeline stages), and `parked` (PB-152 — a human-set manual-hold marker; the hands-off `/plan-my-work` modes 3 & 4 skip any `parked` issue, so groom never enqueues it and auto-drive/top-of-queue never claims it) onto existing projects; new projects get them all on create (PB-70). Also: `subtree <ref>` (open sub-issues of an execute target, PB-81), `blocked-by <ref>` (open blockers — the loop runs these first, PB-94), and `doing` (issues currently in progress, read by `/end-of-day`, PB-94).

**Dual-mode.** Invoked **directly** by the user, you load planning context and reason about the instruction. Invoked **by /plan-my-work** (it sets `PBRAIN_PM_CALLER=plan-my-work` → `caller: plan-my-work`, EXECUTOR MODE), you skip deliberation and just execute exactly what you're told — /plan-my-work already made the decisions.

**Guardrails (D4).** Labels you name are **auto-created**, capped per run (a `skipped_labels` result means the cap was hit — say so). **People and projects are never auto-created** — confirm first. **Manual fallback:** for the ~10% the API can't do (file attachments, deleting an issue, workspace settings, board reordering), don't fail silently — give the exact Plane-UI steps.

## Setup wizard (absorbed from the old /init-plane)

With **no argument** the script runs `probe` → `INIT_PLANE_PROBE` + machine state (`docker`, `docker_running`, `compose`, `selfhost_dir`, `setup_sh`, `plane_config`, `plane_running`, `configured`, `default_url`, `plane_env`, `vhost_port`, `vhost_domain`). **Drive the wizard one step at a time from that state.** This is the same local self-host flow /init-plane had:

1. **Prerequisites.** Plane self-host needs **Docker + Docker Compose running** (≈4 GB RAM, 2 cores). `docker: no` → install Docker Desktop and stop. `docker_running: no` → start it and stop. `compose: no` → update Docker Desktop.
2. **`fetch`** → downloads Plane's official `setup.sh` (`INIT_PLANE_FETCHED`).
3. **`up`** → runs Plane's **own interactive installer** (menu: Install / Start / Stop / …). First time choose **Install** (a big Docker pull), then **Start**. App comes up at **http://localhost** (port 80). (Handle `INIT_PLANE_NEED_FETCH`/`INIT_PLANE_NEED_DOCKER` first.)
4. **Move Plane to its stable URL (default).** As soon as Plane is up, run `vhost` to move it off port 80 to a stable **http://plane.localhost:1800** (so port 80 stays free for other local apps and the URL never collides). Do this **before** the browser step so the account/workspace below live at the final URL. Zero new daemons — it edits Plane's OWN `plane.env` (`APP_DOMAIN` + `LISTEN_HTTP_PORT`, which Plane substitutes into `WEB_URL`/`CORS_ALLOWED_ORIGINS` automatically) and restarts the Plane stack; pbrain's `base_url` gets set automatically when you wire it in step 7 (the vanity host is browser-only). Plane's built-in Caddy is host-agnostic on its listener port, so both the browser URL and pbrain's loopback (`http://127.0.0.1:1800`) hit the same backend. Flags: `--host` (default `plane.localhost`), `--port` (default `1800`), `--plane-home` (override env-file discovery), `--no-restart` (edit only). To stay on plain `http://localhost`, **skip this step** (or undo later with `vhost --remove`).
5. **Account + structure (browser, guide the user).** http://plane.localhost:1800 → sign up (first user = admin) → create a **workspace** (note the **slug** from the URL) → create one or more **projects** (note each **project id**). Suggest modeling umbrella parts as **Modules**, larger tasks as **Issues**, subtasks as **Sub-issues**. (If you skipped step 4, this is http://localhost.)
6. **Token.** Plane → Profile Settings → Personal Access Tokens → Add → copy. Ask the user to paste it; handle as a secret, never echo it.
7. **Wire pbrain → Plane.** For the **local** instance run `config --api-key <token> --workspace <slug> --project <project-id>` (base URL is auto-detected from `plane.env` — `http://127.0.0.1:1800` after `vhost`, else `http://localhost`). For **Cloud or a remote host** run `setup --base-url <url> --api-key <token> --workspace <slug> --project <id>` (no localhost default). Either writes `~/.config/pbrain/plane.json` (mode 0600, never synced). Confirm `PLANE_CONFIGURED`.
8. **Sync the registry.** Run `projects --sync` so all of the workspace's projects are known to pbrain (`PM_PROJECTS` + a JSON array of `{id,name,shortcut}`). Offer to add short `shortcut` codes by editing `plane.json` (e.g. `lt` for Lettuce) — they make `--projects lt,pb` ergonomic.
9. **Verify.** `test` lists the project's states; `ready` shows ready issues. On `PLANE_ERROR`, relay it (bad token, wrong workspace/project, or Plane not fully up) and help fix it — don't loop.

10. **Offer daily backups (PB-17).** Once Plane is verified, offer to turn on a daily snapshot: `backup enable` (default 03:30, local dest, 14-day retention). Ask where it should land — **local** (Time-Machine-covered), an **external volume** (`--dest external --dir /Volumes/<name>/…`), or a **VPS** (`--dest vps --vps-host user@host --vps-path ~/plane-backups`). Run `backup estimate` first if they want to know the footprint. This step is optional — skip it if they decline.

`status` (`INIT_PLANE_STATUS`) shows Docker + Plane container + configured state at any time. Everything is idempotent.

## Backing up Plane (PB-17)

Plane keeps everything that matters in two Docker volumes — Postgres (`*_pgdata`: issues/projects/comments) and MinIO (`*_uploads`: attachments). `backup` snapshots both into one self-describing tarball (`plane-YYYYMMDD-HHMMSS.tar.gz` → `db.dump` from `pg_dump -Fc` + `uploads.tar.gz` + `manifest.json`). It talks to Docker directly, so it works **without Plane wired to pbrain** (no token needed), only a running Plane. Redis/RabbitMQ are ephemeral and excluded.

- `backup estimate` — measure the real current snapshot size + projected retention footprint (`PM_BACKUP_ESTIMATE` / `PBK_ESTIMATE …`). Use this to answer "how big will it be?".
- `backup now [--dir <path>]` — take a snapshot now (`PM_BACKUP`). `--dir` overrides the destination for a one-off.
- `backup enable [--time HH:MM] [--dest local|external|vps] [--dir <path>] [--keep N] [--vps-host …] [--vps-path …] [--vps-port …] [--ssh-key …]` — persist config + install the daily LaunchAgent (`PM_BACKUP_ENABLE`).
- `backup disable` — remove the schedule, keep existing snapshots (`PM_BACKUP_DISABLE`).
- `backup config …` — change settings without touching the schedule (re-installs it if already live) (`PM_BACKUP_CONFIG`).
- `backup status` — schedule, destination, retention, Time-Machine coverage, snapshot count + latest (`PM_BACKUP_STATUS`). `backup list` — the snapshots with sizes (`PM_BACKUP_LIST`).
- `backup run` — the headless entry point the LaunchAgent calls (snapshot → optional VPS upload → prune); logs to `~/.config/pbrain/plane-backup.log`.
- `backup restore <file|latest> --yes` — **destructive**: `pg_restore --clean` + rewrite the uploads volume. Always confirm with the user first; the script also refuses without `--yes` (`PM_BACKUP_RESTORE`). Afterwards, restart Plane workers.

Config lives at `~/.config/pbrain/plane-backup.json` (mode `0600`). **Local backups sit under `~/.config/pbrain/plane-backups`, which Time Machine covers by default** — `backup status` flags it if that path is excluded.

## Ops tokens

- `PM_PROJECTS` — JSON array of `{id,name,shortcut}` (the registry). With `--sync` it was just refreshed from the live workspace. Give a tight read; note any project without a shortcut the user may want to name.
- `PM_READY` — JSON array of ready work items across the chosen projects (`--projects` is a comma list of uuid|name|shortcut; omitted = all registry projects), each tagged with `project`/`project_id` and a full `tie` (`<project_id>:<issue_id>`), sorted by priority → due. Each row also carries `is_sub` (true for sub-issues), `approved` (true when the issue bears the `plan-approved` label; an approved plan lets `/plan-my-work` fast-path its plan stage), and `auto_gates` (PB-94 — the pipeline STAGES this issue is auto-execution cleared for, from its `auto:<stage>` labels; empty → every stage is manual). `--require-approved` filters to approved-only. **`--ordered` (PB-94)** post-processes the stream for the groom→pmw hand-off: it hoists each issue's open **blockers ahead** of the issues they block. `ready` is already **todo-only** (READY_GROUPS = unstarted/started — backlog is excluded), so the ordered stream groom feeds to `/plan-my-work` is todo, blockers-first. Present grouped by project as "what's pickable now." This is the same data `/plan-my-work` packs into blocks.
- `PM_QUEUED` / `PM_CLAIM_NEXT` / `PM_ENQUEUE` (PB-141) — **Plane is the queue.** `queued` returns the issues currently in the **Queued** state, in groom's rank order (`sort_order` ascending) — a read-only peek at what's next. `claim-next --session <token>` is how `/plan-my-work` actually CONSUMES the queue: it atomically claims the top Queued issue for that session (moves it to Planning + stamps a per-session sentinel, then verifies this session won the move) and returns the claimed row, or `null` when the queue is empty. This makes **two parallel `/plan-my-work` sessions pick DIFFERENT issues sequentially** — no collision on the same top (claim+verify; last-write-wins, the loser re-pulls). `enqueue` is how **groom** writes the queue: it takes the ordered ready stream (`ready --ordered`, blockers-first) and MOVES each todo issue into the Queued state with an ascending `sort_order`. Idempotent — re-running re-ranks the same todo set; an issue already in progress (Planning+) is left alone, never pulled back. **Backlog is never touched** (the user's own staging area). Intake (`file`) lands in **Todo** by default; groom promotes Todo → Queued. **PB-146:** `enqueue` ALSO ranks each project's **Done** column by `completed_at` (newest first → smallest `sort_order`); `--no-done` skips it. `enqueue` returns `{queued, done_ranked}`.
- `PM_PROGRESS` — a JSON object keyed by project id: `pct` (done-weight ÷ total, weighted by estimate when present), `counts` (todo/doing/done/dropped), `completed_since` (when `--since DATE` was passed). Render a per-project progress read; lead with what's moving and what's stalled. This is the engine behind `/plan-my-work`'s progress report.
- `PM_REVIEW` — a JSON array of thin issues, each `{tie, project, title, flags}` where flags ⊆ `no_description | no_estimate | no_priority | no_subissues`. **Read-only — it proposes nothing on its own.** Now **walk the list ONE issue at a time**: for each, suggest a concrete enrichment (a description, an estimate in hours, a priority, or a sub-issue breakdown) and **ask the user to confirm or edit it before writing anything**. Only on an explicit yes, collect the confirmed edits into `[{"tie":"…","field":"description|priority|estimate|target_date|subissue","value":…}]` and apply them with `enrich --edits '<json>'`. **Never auto-commit; never enrich a flag the user declined — on a decline, leave the issue flagged and move on.** Absent fields are reported as "can't assess," not thin, so you won't be asked to fill a field Plane simply doesn't return.
- `PM_EXPLODE` — followed by a JSON object for ONE issue the user wants broken down interactively (`explode <ref>`). **Read-only.** Branch on `status`: `none` (offer to create it), `ambiguous` (a `candidates` shortlist — ask which, then re-run `explode`), `error` (relay), or `ok`. On `ok` you also get `tie, id, title, description, priority, state, has_estimate_scale, estimate_points, existing_subissues`. Then run the **Socratic walk** the script emits (the same spirit as `/discuss` + `/journal` open questions): **one question at a time** via the `AskUserQuestion` tool (suggested options + its free-form "Other"; plain-conversational fallback when the tool is absent, e.g. Codex) to draw out the definition of done, the natural seams, ordering/deps, sizing (~30m–1h sub-issues), and out-of-scope. Confirm, then write the refined parent **description** + each child as a `subissue` in one `update --edits` batch (relations need a second pass once children exist). **Never auto-commit; don't duplicate a title already in `existing_subissues`.**
- `PM_SPEC` — followed by a JSON object for ONE issue (`spec <ref>`), the spec/approval gate (PB-45). **Read-only.** Branch on `status` exactly like `PM_EXPLODE`: `none`/`ambiguous`/`error`/`ok`. On `ok` you also get `tie, id, title, description, description_html, has_plan, approved, approved_label, auto_gates, priority, state`, plus `comments` (the user's issue comments, oldest→newest) and `comments_authoritative: true`. (`auto_gates` is the PB-94 per-gate clearance list — which lifecycle gates auto-advance for this issue; `task execute` reads it at each gate.) **User comments are AUTHORITATIVE (PB-61)** — they override the description and any model-added plan content; the newest comment wins where comments disagree. Read the comments first, draft the plan to honour them, and if a comment contradicts the description say so in one line so the stale description gets fixed. Then run the **Socratic walk** the script emits — **one question at a time** (`AskUserQuestion`, plain-conversational fallback on Codex) drawing out done/approach/touchpoints/risks/out-of-scope/verify — to write a tight `## Implementation Plan` into the issue **description** (preserve the existing description; append/replace only the plan section, using `description_html`). Approval is a **separate** decision: only on an explicit yes, `tag "<tie>" --add plan-approved`. An approved plan is what lets `/plan-my-work task execute` skip its live planning gate. **Never auto-commit; don't rewrite an already-`approved` plan without re-opening it.** The `--read` flag (and executor mode) emit ONLY the JSON, no walk — that's how `task execute` reads the recorded plan + approval state.
- `PM_FILE` — followed by a JSON object for FILING new work from a free-text `dump` (`file "<dump>"`, aliases `create`/`track`/`capture`, PB-67). The **generic work-item intake & triage convention** — any type, inferred from the dump. **Read-only** until you create. Branch on `status`: `need_project` / `unknown_project` (show `projects`, ask which, re-run with `--project`) or `ok`. On `ok` you get `dump, project, project_id, existing_labels, work_types` (type→convention label), `type_body_shape` (type→body headings), `convention_labels`, `severity_priority`, `has_estimate_scale`, `estimate_points`, and `recent_open_items` (open items for **dedupe** — offer to comment on an existing one rather than file a duplicate). **First EXPLODE the dump** (silently infer type/title/body/priority from `type_body_shape`). Then pick the path by the **`PM_FAST`** env var the script exports: `PM_FAST=yes` → **fast path** (show the exploded item, one confirm/edit, create — aim for zero extra questions); `PM_FAST=no` → **full path** (Socratic build-up, one question at a time, covering type → body gaps → sub-issues → labels → estimate (only if `has_estimate_scale`) → priority → deadline). Synthesize, get an explicit yes, then create via `issue …` and set body + the type's convention label (+ estimate/sub-issues) on the returned tie in one `update --edits` batch. **Never auto-file; never fake a created issue.** Bug severity sets priority via `severity_priority`; the convention labels exist in every project via PB-70's seeding.
- `PM_ENRICH` — the confirmed writes were applied; relay the per-edit `ok`/`error` summary in one line each.
- `PM_MOVE` / `PM_PRIORITY` / `PM_TIMELINE` — a single-issue write succeeded (or returned `ok:false` with an error); confirm it in one line. `move <tie> --to <todo|doing|done|blocked|dropped>`, `priority <tie> --value <urgent|high|medium|low|none>`, `timeline <tie> --target-date <YYYY-MM-DD>`.
- `PM_ISSUE` — JSON `{project_id, project, issue}` where `issue` is the raw Plane response for the newly created work item. Report the issue's `sequence_id` (human-readable number) and title. On `PLANE_ERROR`, relay it. Usage: `issue --project <uuid|name|shortcut> --title <title> [--priority urgent|high|medium|low|none] [--target-date YYYY-MM-DD]`. **Internal primitive, NOT a routing entry point (PB-112):** the bare `issue` create verb is the low-level building block `file`'s STEP 3 (and executor mode) call to actually create the issue — it is deliberately kept OUT of the NL routing catalogue so "file a bug" routes through the `file` triage convention, never a hand-assembled raw create. Don't surface it as an intake option for a user's "file/create/track this" request; route those through `file`.
- `PM_PROJECT_CREATE` — JSON `{id, name, shortcut}` for the newly created Plane project. It has already been added to the local registry — no `projects --sync` needed. Report the name, id, and shortcut (if given). On `PLANE_ERROR`, relay it. Usage: `project-create --name <name> [--shortcut <alias>]`.
- `PM_WORKDIR` — the per-project **working location** used by `/plan-my-work task execute` (PB-40): where that project's tasks get implemented. Stored in `plane.json` `projects[].work` = `{path, kind, base_branch, isolation}` — a plain local path, no secret, no network call. Usage: `workdir` (list the configured map) · `workdir <ref> --path <abs> [--kind conductor|repo] [--base-branch <b>] [--isolation worktree|branch]` (set; defaults `kind=repo`, `base_branch=main`, `isolation=worktree`, so the user's main checkout is never disturbed — `task execute` isolates via worktree/branch) · `workdir <ref> --clear` (remove). The path must already exist (`task execute` never spawns a workspace; it `cd`s into a pre-existing repo). `projects --sync` preserves `work`. Report the project + resulting `work` in one line.
- `PM_PRUNE_MERGED` — **post-merge worktree GC** (PB-141 follow-on; pure git, no Plane, so it runs unconfigured). Sweeps every `pbrain/*` worktree under `--repo <path>` (default cwd) whose branch is **content-merged** into base (`--base`, default `origin/main`) **and** whose working tree is **clean**, removing the worktree + its local branch. The merged-check is **file-scoped** (does base already match the branch on every file the branch touched?), so it is **squash-merge safe** where a raw `git diff base..B` or `git cherry` give false-positives. Discovery is via `git worktree list --porcelain` (authoritative — handles any worktree root). Outputs one line per worktree (`PRUNED` / `KEPT-unmerged` / `KEPT-dirty` / `KEPT-error` / `SKIPPED-not-pbrain`) + a `summary: repo=… base=… pruned=N kept=M skipped=K` line, plus `PMR_ERR <reason>` for not-a-git-repo / bad base. The primary checkout and non-`pbrain/*` worktrees are never touched; parked/unmerged/dirty worktrees are kept. Removes by default; `--dry-run` previews; `--remote-prune` also runs `git remote prune origin`. This is what `/plan-my-work`'s land stage calls after a merge — and what an **agent clearing PRs out-of-session** should run to GC the stale worktrees those merges left behind (the gap that piled up 7 worktrees before this existed).
- `PM_ROUTE` — a natural-language instruction. Followed by `instruction:`, `caller:` (`direct` or the calling command), the registry, and — when direct — the planning context, then the runtime **catalogue** to route against. Resolve → map → execute → report.
- `PM_FIND` — JSON array of candidate issue cards `{tie, id, issue_id, project, title, state, priority, parent}` for a URL / `PB-26` / sequence / name fragment. One card → act; several → disambiguate; zero → offer to create.
- `PM_SUBTREE` — followed by a JSON object resolving ONE execute TARGET that may be a PARENT (`subtree <ref>`, PB-81). **Read-only.** Branch on `status` like `PM_FIND`: `none`/`ambiguous`/`error`/`ok`. On `ok` you get `tie, id, issue_id, title, priority, state, project, project_id, has_open_children`, and `children` — the parent's OPEN sub-issues as ready-shaped rows (full `tie`/`is_sub`/`approved`/`priority`/`due`/`est_h`), sorted priority → due → id (done/cancelled children excluded). `has_open_children: false` (a leaf, or a parent whose children all landed) → the issue itself is the unit of work. `has_open_children: true` → the parent is ONE logical target executed as SEPARATE SEQUENTIAL UNITS: `/plan-my-work task execute` drives each child through its own branch/PR/double-gated-merge in order, then closes the parent only after the last child merges. This is what `task execute <parent-ref>` uses so targeting a parent no longer fans out uncontrollably.
- `PM_UPDATE` / `PM_TAG` / `PM_COMMENT` / `PM_ASSIGN` / `PM_REPARENT` / `PM_CYCLE` / `PM_MODULE` — a write applied via the generic `enrich` path. Each prints a per-edit `{ok|error, field, …}` summary; relay it in one line. `update --edits '[{tie,field,value}]'` is the batch form (one creation-guard + cache for the whole set). `assign --to` resolves a name/email; an ambiguous name comes back as an error listing candidates — pick by id. A `skipped_labels` field means the auto-create cap was hit.
- `PM_LABELS` / `PM_MEMBERS` / `PM_CYCLES` / `PM_MODULES` — JSON lookup tables (name→uuid) for a project; use them to resolve a vague reference, or to show the user what exists.
- `PM_ESTIMATES` — JSON `{project, project_id, hours_per_point, scale}` where `scale` is the project's estimate scale (`{name, type, points:{value→estimate_point uuid}}`) or `null`. Plane's **public** token API can neither list nor create estimate points (404) — only the cookie-auth **internal** endpoint (`/api/workspaces/<ws>/projects/<id>/estimates/`) exposes them. The scale is **fetched LIVE on every run** (in `ready`/`progress`/`review`/`enrich` via `ensure_estimate_scale`) and held **in-memory only — never cached to disk** (a user can edit estimates in Plane any time, so we always read real-time). **If estimates exist on the project it's used; otherwise skipped silently** (falls back to the flat `default_est_h`). To give a project that has none a scale, `estimates --project <R> --create` creates **and activates** one (default Fibonacci points; idempotent — reuses an existing scale, just (re)activates it via `project.estimate`). `--template fibonacci|linear|squares|hours|tshirt|difficulty` picks a preset (`hours` = numeric work-hour buckets `1,2,4,8,16`, pbrain's planning-optimised scale; `difficulty` = Easy/Medium/Hard/Very Hard), `--type points|categories|time` + `--scale a,b,c` build a custom one, and `--replace` deletes any existing scale first to switch type — **⚠️ deleting a scale clears every issue estimate on that project (they reference the old scale's point UUIDs), so re-backfill after a `--replace`.** **Caveat:** only **points** (numeric) scales feed `/plan-my-work` block-packing; t-shirt/`categories` scales are creatable and settable on issues but don't convert to hours (those issues fall back to `default_est_h`). Live fetch needs internal auth, persisted once via `estimates --from-browser [--browser brave|chrome|chromium]` (pulls the session cookie from the local Chromium cookie store — macOS, v10 — re-pulled fresh each run and **auto-refreshed from the browser on expiry**, the recommended local-self-host path), or `estimates --session-cookie '<cookie>'`, or `estimates --email <e> --password <p>` (logs in + auto-refreshes on 401). The only things persisted to `plane.json` are the internal-auth knobs, `--hours-per-point N` (the points→hours factor `/plan-my-work` packs blocks with, default 1.0), and `--import-json '<file|json>'` (an offline fallback scale for when the internal API is unreachable, e.g. Plane Cloud). The `estimate` field (in `update`/`enrich`) resolves a story-point value (e.g. `"3"`) to its `estimate_point` UUID and writes it (shows in the Plane UI), and `review` flags `no_estimate` on scale-having projects. **Never echo the cookie/password.**
- `PM_BACKUP*` — the Plane backup verbs (see **Backing up Plane** above): `PM_BACKUP` (a `now`/`run` snapshot — report the written path + size, relay any `PBK_ERR`/`PBK_WARN`), `PM_BACKUP_ESTIMATE` + `PBK_ESTIMATE db_bytes=… uploads_bytes=… per_snapshot_bytes=… keep=… retained_bytes=…` (give the human read beneath it), `PM_BACKUP_ENABLE`/`_DISABLE`/`_CONFIG`/`_STATUS`/`_LIST`/`_RESTORE`. `backup` never needs a configured Plane (it drives Docker directly), so it runs even when the ops above emit `PM_NOT_CONFIGURED`.
- `PM_TEST` / `PM_SETUP` / `PM_COMPLETED` / `PLANE_CONFIGURED …` / `PLANE_OK …` / `PLANE_ERROR …` — config/verify results. On `PLANE_ERROR`, relay the message and help fix the config; don't loop.

Keep reads tight, lead with what needs attention, and let the user drive. This is a commander, not a coach.
