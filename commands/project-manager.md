Run this with your shell first (substituting any argument for `$ARGUMENTS`), then follow the INSTRUCTIONS below based on the token it prints:

```bash
bash "${PBRAIN_DEV_DIR:-${CLAUDE_PLUGIN_ROOT:-$HOME/.claude/plugins/marketplaces/pbrain}}/commands/project-manager.sh" "$ARGUMENTS"
```

`/project-manager` is the operator between pbrain and **Plane** (makeplane). Plane owns the task tree (Module → Issue → Sub-issue) and the UI; pbrain reads ready work and writes status back through two seams. One pbrain "project" = one Plane PROJECT; a workspace holds many, tracked in a small registry (`projects [--sync]`). **Plane is pbrain's sole project backend** — task planning and project progress require it. When Plane isn't configured the ops emit `PM_NOT_CONFIGURED` (a friendly "set Plane up" note); the setup family still runs.

**Never print or echo the Plane API token back to the user — treat it as a secret at every step.**

## Driving Plane in plain words (the main path)

The user mostly won't type verbs — they'll say what they want. **Any first word that isn't a known verb is treated as a natural-language instruction and routed.** You can also force it with `route <words>`. The script prints `PM_ROUTE` + a compact **capability catalogue** + (on a direct invocation) the user's daily/weekly/monthly plan context so your routing is goal-aware. Then you:

1. **Resolve** the issue(s) with `find "<link | PB-26 | name fragment>"` → candidate cards `{tie, id, title, state, project}`. One → use its `tie`; several → ask which; zero → offer to create.
2. **Map** the instruction to specific verbs (one ask can be several ops; batch with `update --edits`).
3. **Confirm only when it matters** — irreversible ops, ambiguous targets, or creating a person/project. Routine edits just apply.
4. **Execute** and report one tight line per issue; relay any `PLANE_ERROR`.

**The write catalogue** (each is a verb; `update --edits '[{tie,field,value}]'` does any of them, batched): `find` · `move` · `priority` · `timeline` · `tag/untag/labels` · `assign` (by name/email/uuid) · `comment` · `reparent` · `cycle` · `module` · `issue` · `project-create` · `description`/`title`/`start_date` · `relation:<type>` · `subissue` · `link`. Listers `labels|members|cycles|modules` give the name→uuid tables.

**Dual-mode.** Invoked **directly** by the user, you load planning context and reason about the instruction. Invoked **by /plan-my-work** (it sets `PBRAIN_PM_CALLER=plan-my-work` → `caller: plan-my-work`, EXECUTOR MODE), you skip deliberation and just execute exactly what you're told — /plan-my-work already made the decisions.

**Guardrails (D4).** Labels you name are **auto-created**, capped per run (a `skipped_labels` result means the cap was hit — say so). **People and projects are never auto-created** — confirm first. **Manual fallback:** for the ~10% the API can't do (file attachments, deleting an issue, workspace settings, board reordering), don't fail silently — give the exact Plane-UI steps.

## Setup wizard (absorbed from the old /init-plane)

With **no argument** the script runs `probe` → `INIT_PLANE_PROBE` + machine state (`docker`, `docker_running`, `compose`, `selfhost_dir`, `setup_sh`, `plane_config`, `plane_running`, `configured`, `default_url`, `plane_env`, `vhost_port`, `vhost_domain`). **Drive the wizard one step at a time from that state.** This is the same local self-host flow /init-plane had:

1. **Prerequisites.** Plane self-host needs **Docker + Docker Compose running** (≈4 GB RAM, 2 cores). `docker: no` → install Docker Desktop and stop. `docker_running: no` → start it and stop. `compose: no` → update Docker Desktop.
2. **`fetch`** → downloads Plane's official `setup.sh` (`INIT_PLANE_FETCHED`).
3. **`up`** → runs Plane's **own interactive installer** (menu: Install / Start / Stop / …). First time choose **Install** (a big Docker pull), then **Start**. App comes up at **http://localhost** (port 80). (Handle `INIT_PLANE_NEED_FETCH`/`INIT_PLANE_NEED_DOCKER` first.)
4. **Move Plane to its stable URL (default).** As soon as Plane is up, run `vhost` to move it off port 80 to a stable **http://plane.localhost:1800** (so port 80 stays free for other local apps and the URL never collides). Do this **before** the browser step so the account/workspace below live at the final URL. Zero new daemons — it edits Plane's OWN `plane.env` (`APP_DOMAIN` + `LISTEN_HTTP_PORT`, which Plane substitutes into `WEB_URL`/`CORS_ALLOWED_ORIGINS` automatically) and restarts the Plane stack; pbrain's `base_url` gets set automatically when you wire it in step 7 (the vanity host is browser-only). Plane's built-in Caddy is host-agnostic on its listener port, so both the browser URL and pbrain's loopback (`http://127.0.0.1:1800`) hit the same backend. Flags: `--host` (default `plane.localhost`), `--port` (default `1800`), `--plane-home` (override env-file discovery), `--no-restart` (edit only). To stay on plain `http://localhost`, **skip this step** (or undo later with `vhost --remove`).
5. **Account + structure (browser, guide the user).** http://plane.localhost:1800 → sign up (first user = admin) → create a **workspace** (note the **slug** from the URL) → create one or more **projects** (note each **project id**). Suggest modeling umbrella parts as **Modules**, larger tasks as **Issues**, subtasks as **Sub-issues**. (If you skipped step 4, this is http://localhost.)
6. **Token.** Plane → Profile Settings → Personal Access Tokens → Add → copy. Ask the user to paste it; handle as a secret, never echo it.
7. **Wire pbrain → Plane.** For the **local** instance run `config --api-key <token> --workspace <slug> --project <project-id>` (base URL is auto-detected from `plane.env` — `http://127.0.0.1:1800` after `vhost`, else `http://localhost`). For **Cloud or a remote host** run `setup --base-url <url> --api-key <token> --workspace <slug> --project <id>` (no localhost default). Either writes `~/.config/pbrain/plane.json` (mode 0600, never synced). Confirm `PLANE_CONFIGURED`.
8. **Sync the registry.** Run `projects --sync` so all of the workspace's projects are known to pbrain (`PM_PROJECTS` + a JSON array of `{id,name,shortcut}`). Offer to add short `shortcut` codes by editing `plane.json` (e.g. `lt` for Lettuce) — they make `--projects lt,pb` ergonomic.
9. **Verify.** `test` lists the project's states; `ready` shows ready issues. On `PLANE_ERROR`, relay it (bad token, wrong workspace/project, or Plane not fully up) and help fix it — don't loop.

`status` (`INIT_PLANE_STATUS`) shows Docker + Plane container + configured state at any time. Everything is idempotent.

## Ops tokens

- `PM_PROJECTS` — JSON array of `{id,name,shortcut}` (the registry). With `--sync` it was just refreshed from the live workspace. Give a tight read; note any project without a shortcut the user may want to name.
- `PM_READY` — JSON array of ready work items across the chosen projects (`--projects` is a comma list of uuid|name|shortcut; omitted = all registry projects), each tagged with `project`/`project_id` and a full `tie` (`<project_id>:<issue_id>`), sorted by priority → due. Present grouped by project as "what's pickable now." This is the same data `/plan-my-work` packs into blocks.
- `PM_PROGRESS` — a JSON object keyed by project id: `pct` (done-weight ÷ total, weighted by estimate when present), `counts` (todo/doing/done/dropped), `completed_since` (when `--since DATE` was passed). Render a per-project progress read; lead with what's moving and what's stalled. This is the engine behind `/plan-my-work`'s progress report.
- `PM_REVIEW` — a JSON array of thin issues, each `{tie, project, title, flags}` where flags ⊆ `no_description | no_estimate | no_priority | no_subissues`. **Read-only — it proposes nothing on its own.** Now **walk the list ONE issue at a time**: for each, suggest a concrete enrichment (a description, an estimate in hours, a priority, or a sub-issue breakdown) and **ask the user to confirm or edit it before writing anything**. Only on an explicit yes, collect the confirmed edits into `[{"tie":"…","field":"description|priority|estimate|target_date|subissue","value":…}]` and apply them with `enrich --edits '<json>'`. **Never auto-commit; never enrich a flag the user declined — on a decline, leave the issue flagged and move on.** Absent fields are reported as "can't assess," not thin, so you won't be asked to fill a field Plane simply doesn't return.
- `PM_ENRICH` — the confirmed writes were applied; relay the per-edit `ok`/`error` summary in one line each.
- `PM_MOVE` / `PM_PRIORITY` / `PM_TIMELINE` — a single-issue write succeeded (or returned `ok:false` with an error); confirm it in one line. `move <tie> --to <todo|doing|done|blocked|dropped>`, `priority <tie> --value <urgent|high|medium|low|none>`, `timeline <tie> --target-date <YYYY-MM-DD>`.
- `PM_ISSUE` — JSON `{project_id, project, issue}` where `issue` is the raw Plane response for the newly created work item. Report the issue's `sequence_id` (human-readable number) and title. On `PLANE_ERROR`, relay it. Usage: `issue --project <uuid|name|shortcut> --title <title> [--priority urgent|high|medium|low|none] [--target-date YYYY-MM-DD]`.
- `PM_PROJECT_CREATE` — JSON `{id, name, shortcut}` for the newly created Plane project. It has already been added to the local registry — no `projects --sync` needed. Report the name, id, and shortcut (if given). On `PLANE_ERROR`, relay it. Usage: `project-create --name <name> [--shortcut <alias>]`.
- `PM_ROUTE` — a natural-language instruction. Followed by `instruction:`, `caller:` (`direct` or the calling command), the registry, and — when direct — the planning context, then the runtime **catalogue** to route against. Resolve → map → execute → report.
- `PM_FIND` — JSON array of candidate issue cards `{tie, id, issue_id, project, title, state, priority, parent}` for a URL / `PB-26` / sequence / name fragment. One card → act; several → disambiguate; zero → offer to create.
- `PM_UPDATE` / `PM_TAG` / `PM_COMMENT` / `PM_ASSIGN` / `PM_REPARENT` / `PM_CYCLE` / `PM_MODULE` — a write applied via the generic `enrich` path. Each prints a per-edit `{ok|error, field, …}` summary; relay it in one line. `update --edits '[{tie,field,value}]'` is the batch form (one creation-guard + cache for the whole set). `assign --to` resolves a name/email; an ambiguous name comes back as an error listing candidates — pick by id. A `skipped_labels` field means the auto-create cap was hit.
- `PM_LABELS` / `PM_MEMBERS` / `PM_CYCLES` / `PM_MODULES` — JSON lookup tables (name→uuid) for a project; use them to resolve a vague reference, or to show the user what exists.
- `PM_ESTIMATES` — JSON `{project, project_id, hours_per_point, scale}` where `scale` is the project's estimate scale (`{name, type, points:{value→estimate_point uuid}}`) or `null`. Plane's **public** token API can neither list nor create estimate points (404) — only the cookie-auth **internal** endpoint (`/api/workspaces/<ws>/projects/<id>/estimates/`) exposes them. The scale is **fetched LIVE on every run** (in `ready`/`progress`/`review`/`enrich` via `ensure_estimate_scale`) and held **in-memory only — never cached to disk** (a user can edit estimates in Plane any time, so we always read real-time). **If estimates exist on the project it's used; otherwise skipped silently** (falls back to the flat `default_est_h`). To give a project that has none a scale, `estimates --project <R> --create` creates **and activates** one (default Fibonacci points; idempotent — reuses an existing scale, just (re)activates it via `project.estimate`). `--template fibonacci|linear|squares|hours|tshirt|difficulty` picks a preset (`hours` = numeric work-hour buckets `1,2,4,8,16`, pbrain's planning-optimised scale; `difficulty` = Easy/Medium/Hard/Very Hard), `--type points|categories|time` + `--scale a,b,c` build a custom one, and `--replace` deletes any existing scale first to switch type — **⚠️ deleting a scale clears every issue estimate on that project (they reference the old scale's point UUIDs), so re-backfill after a `--replace`.** **Caveat:** only **points** (numeric) scales feed `/plan-my-work` block-packing; t-shirt/`categories` scales are creatable and settable on issues but don't convert to hours (those issues fall back to `default_est_h`). Live fetch needs internal auth, persisted once via `estimates --from-browser [--browser brave|chrome|chromium]` (pulls the session cookie from the local Chromium cookie store — macOS, v10 — re-pulled fresh each run and **auto-refreshed from the browser on expiry**, the recommended local-self-host path), or `estimates --session-cookie '<cookie>'`, or `estimates --email <e> --password <p>` (logs in + auto-refreshes on 401). The only things persisted to `plane.json` are the internal-auth knobs, `--hours-per-point N` (the points→hours factor `/plan-my-work` packs blocks with, default 1.0), and `--import-json '<file|json>'` (an offline fallback scale for when the internal API is unreachable, e.g. Plane Cloud). The `estimate` field (in `update`/`enrich`) resolves a story-point value (e.g. `"3"`) to its `estimate_point` UUID and writes it (shows in the Plane UI), and `review` flags `no_estimate` on scale-having projects. **Never echo the cookie/password.**
- `PM_TEST` / `PM_SETUP` / `PM_COMPLETED` / `PLANE_CONFIGURED …` / `PLANE_OK …` / `PLANE_ERROR …` — config/verify results. On `PLANE_ERROR`, relay the message and help fix the config; don't loop.

Keep reads tight, lead with what needs attention, and let the user drive. This is a commander, not a coach.
