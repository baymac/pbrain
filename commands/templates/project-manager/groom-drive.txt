ASSESS & LABEL — this is a MAJOR part of grooming, not a preamble. The nightly heuristic
is deliberately conservative (it only grants auto:implement to approved+small+unblocked
issues). YOU have the judgment it lacks: read each queued issue and decide how far it
should auto-run, then set the labels. For each id in `## Queue — ordered`:
  1. Read the issue: `${PM_CMD} spec "<tie>" --read` → has_plan, approved, description,
     comments (AUTHORITATIVE — newest wins), blocked_by, current auto_gates, and labels.
  1a. QUALITY GATE (judgment, not presence). The thin-check upstream only catches EMPTY
     fields — a one-letter or placeholder description ("x", "wip", "todo", "tbd", "?") or a
     vague target-less one-liner ("fix the thing", "make it better") PASSES it but is NOT
     good enough to run. You already have the description/priority/estimate in hand, so judge
     QUALITY before labeling:
       • Description — does it say WHAT to change and HOW you'd know it's done? Placeholder /
         single-word / vague-no-target ⇒ not good enough.
       • Priority — plausible for the work? A clearly high-impact/blocking issue left at
         low/none, or a trivial chore at urgent, is wrong ⇒ reset it.
       • Estimate (only if the project has a scale) — set and roughly plausible for scope?
         Missing/absurd ⇒ set a sensible one.
     If it FAILS any check, ENRICH it now — exactly like a `## Needs review` item
     (`${PM_CMD} enrich`/`priority`/`estimate`/`update`) — then continue to labeling.
     Autonomous mode: decide and apply, don't ask. Interactive: propose, then apply.
     Be CONSERVATIVE — improve genuinely-thin fields; do NOT rewrite already-adequate prose.
     IDEMPOTENCY: if the issue ALREADY carries `auto:groomed`, SKIP this gate (a prior run

     stage — it never affects auto-advance.)
