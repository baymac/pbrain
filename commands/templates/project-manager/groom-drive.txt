AUTONOMOUS MODE (headless nightly run, no human present). If you are running

This is the whole job in autonomous mode: turn a raw todo list into a groomed, labeled,
runnable queue overnight — using judgment in place of the questions you'd otherwise ask.

READ FIRST. Open the `## Queue — ordered` table in $GROOM_DATA_FILE. The `Auto` column
shows the stages the NIGHTLY mechanical heuristic pre-granted (a conservative floor).
An empty queue → nothing to drive; say so and stop (the `## Needs review` list still
stands for the user to enrich). Otherwise, do ASSESS & LABEL, then DRIVE.

ASSESS & LABEL — this is a MAJOR part of grooming, not a preamble. The nightly heuristic
is deliberately conservative (it only grants auto:implement to approved+small+unblocked
issues). YOU have the judgment it lacks: read each queued issue and decide how far it
should auto-run, then set the labels. For each id in `## Queue — ordered`:
  1. Read the issue: `${PM_CMD} spec "<tie>" --read` → has_plan, approved, description,
     comments (AUTHORITATIVE — newest wins), blocked_by, current auto_gates.
  2. JUDGE which stages are safe to auto-advance (you may grant MORE than the nightly
     floor, or REMOVE one it set that you judge unwarranted):
       • auto:plan      — if the issue is well-formed enough to plan. Low-risk; default yes.
       • auto:implement — if the work is clearly SIMPLE and low-risk: small, well-scoped,
                          no thorny unknowns, blockers resolved. A complicated or vague
                          issue does NOT get it (let it park at plan for your review).
                          You may grant this from the description even with NO saved plan,
                          when the work is obviously easy.
       • auto:test      — if testing is straightforward (clear test surface / existing
                          test patterns). Skip for pure docs/chore where tests don't apply.
       • auto:ship      — if shipping intent is clear (a real change headed for a PR).
       • auto:land      — NEVER. Merge is always a manual, irreversible gate.
  3. APPLY your decision: `${PM_CMD} tag "<tie>" --add "auto:implement,auto:test,auto:ship"`
     for the stages you grant; `${PM_CMD} tag "<tie>" --remove "auto:test"` to strip one
     the heuristic over-granted. Labels are independent + stop-at-first-gap, so only grant
     a contiguous run from plan (granting ship without implement just parks at implement).
  4. Note the final stage set per id; you'll record it in `## Auto-work` after driving.
Conservative bias: when unsure, grant LESS — a parked issue is a safe review point, an
over-granted one auto-runs code you didn't vet. Never grant auto:land.

DRIVE THE QUEUE — for each id in `## Queue — ordered`, in order:
  1. Hand it to the execution loop: `/plan-my-work <PB-id>`. That command owns the
     whole 5-stage pipeline (plan → implement → test → ship → land), the auto:<stage>
     label checks, the worktree, the PR, the merge, and the PARK. Do NOT reimplement
     any of it here — just invoke it per id.
  2. Each id runs until it either completes (landed) or PARKS at the first stage whose
     `auto:<stage>` label is absent. pmw writes the park breadcrumb onto the issue
     itself, so you don't manage that — you just move to the next queued id.
  3. RECORD the outcome in the grooming-data file's `## Auto-work` section (append one
     line per id): `- **<PB-id>** <title> — <landed | parked at <stage>>; <PR/branch
     link if any>`. This is the morning-review record of how far the night got.

INVARIANTS (owned by execute.txt — never weakened here):
  • The merge (stage land) is irreversible. Without `auto:land` it is a manual park
    point; even WITH `auto:land`, CI must be green — a red CI parks the issue, never
    merges. groom never types the confirm for you.
  • groom DOES assign auto:plan/implement/test/ship by judgment (the ASSESS & LABEL
    phase above) — that's intended grooming. But it NEVER assigns `auto:land`: the
    final merge is always the user's manual gate. Granting a stage = trusting it to run
    unattended, so bias conservative and leave the irreversible step to the user.
  • Thin issues (in `## Needs review`) are NOT in the queue — they need enrichment
    first and must not be driven.

When the queue is exhausted (or you stop), give one tight summary: which ids landed,
which parked (and at which stage), and "review the grooming data at $GROOM_DATA_FILE,
then run `/plan-my-work <PB-id>` to resume any parked issue." Stop here.
