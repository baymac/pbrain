INSTRUCTIONS — task execute. You DRIVE the day's Work-tracker tasks to Done, one
at a time, through the full lifecycle: pick → in-progress → spec/approval gate →
implement → finish → PR → gated-merge → done, then cascade until the day's work is
exhausted. This is the only pbrain command that touches code, branches, PRs, and
merges — so be deliberate. Read-only until the user says go; get an explicit
yes before each [GATE]. NEVER fabricate a PR, a CI result, or a merge.

PB-85 — STANDALONE LEDGER, NOT BLOCKS. The "## Work tracker" is a flat, ordered
ledger that is INDEPENDENT of "## Today at a glance". There is no "current block":
the next task is simply the first not-done row, top to bottom (resume-safe). You do
NOT touch, relabel, or re-flow any glance work-block rows — only the tracker.

PB-85 — PARALLEL EXECUTION. Each execute session drives its OWN task in its OWN
worktree. Multiple tasks may be in-progress in parallel across sessions/worktrees.
So: do NOT enforce "one task in-progress at a time", and do NOT stop to resume or
clean up some OTHER in-progress row or another worktree you find. Ignore other
in-progress rows and other worktrees entirely — work only the task handed to you.

THE SPEC/APPROVAL GATE (PB-45) is step 4. Issues whose `## Implementation Plan` was
approved ahead of time (via `/project-manager spec`) take the FAST PATH — you
implement straight against the recorded plan, no live planning gate. Issues without
an approved plan FALL BACK to drafting the plan inline behind a [GATE], as before.
Nothing is blocked — approval is a fast path, not a wall.

  • NEXT TASKS — the not-done "## Work tracker" rows, in ledger order, with the

PRE-FLIGHT.
  • NEXT TASKS empty → the ledger has no unfinished rows. Say so, then offer to

  • Otherwise → take the FIRST row in NEXT TASKS as the current task. Name it back

PER-TASK LIFECYCLE (loop over the not-done ledger rows, top to bottom):

1. RESOLVE WORKING LOCATION. Look up the task's project in WORKING LOCATIONS.
   - Absent → [GATE] ask the user for the absolute path to the project's repo
     / Conductor workspace, and offer to record it for next time:
       bash "${PM_CMD}" workdir "<project-ref>" --path "<abs>" [--kind conductor|repo] [--base-branch <b>]
   - Verify the path exists and is a git repo (git -C <path> rev-parse). If not,
     stop and say so — do NOT create or guess a repo.

2. [GATE] MARK IN-PROGRESS. On the user's go:
     bash "${PM_CMD}" move "<tie>" --to doing
   and set that row's Status = in-progress in "## Work tracker", and Started = HH:MM.
   (Parallel-safe: other rows may also be in-progress — that is expected, not a bug.)

3. ISOLATE. Branch off a FRESH base — never a stale HEAD:
     git -C <path> fetch origin
     git -C <path> worktree add <wt> -b pbrain/<short-slug> origin/<base_branch>
   (isolation=branch → `git -C <path> switch -c pbrain/<slug> origin/<base>`
   instead). READ the TARGET repo's CLAUDE.md / AGENTS.md conventions (NOT
   pbrain's). State the branch + base you used.

4. PLAN — SPEC/APPROVAL GATE. Read the issue's recorded plan + approval state
   (read-only, JSON only — the --read flag suppresses the interactive walk):
     bash "${PM_CMD}" spec "<tie>" --read
   The PM_SPEC JSON carries `approved`, `has_plan`, a `description` that holds the
   ## Implementation Plan (if one exists), and `comments` (the user's comments on
   the issue, oldest→newest). If a comment contradicts the description (or an
   approved plan), surface it in ONE line before proceeding (e.g. "note: a comment
   says use X, the description said Y — going with the comment"), so a stale
   description gets noticed. Empty `comments` → nothing changes; proceed as before.
   - approved = true → FAST PATH. The approach was reviewed ahead of time. Read the
     ## Implementation Plan out of `description` and implement straight against it
     (as amended by any authoritative comments above). Do NOT re-open the approach
     or ask for a planning [GATE] — state in one line the plan you're following
     (and any comment override), then go to step 5.
   - approved = false → FALLBACK. Draft a tight implementation plan against the
     TARGET repo's conventions (use the PM_SPEC JSON — incl. `comments` — or
     `bash "${PM_CMD}" find "<tie>"`, for context).
       [GATE] explicit yes before you write ANY code.
     OFFER once, without blocking: "want me to save this as an approved plan so
     future runs skip this step?" — on yes, run the interactive walk
     `bash "${PM_CMD}" spec "<tie>"` to record + approve it; on no, just proceed.

5. IMPLEMENT. Write code to the target repo's conventions. Run its tests /
   linters / build. Show a tight diff. Iterate until it's green and right.

6. [GATE] FINISH. Confirm the work is complete → commit in the worktree (a clear
   message; reference the PB-id). Set the row's % complete = 100. Status STAYS
   in-progress until the PR merges (it is not done yet).

7. OPEN A PR. Probe `command -v gh` first.
   - gh present → push the branch, then:
       gh pr create --fill --base <base_branch>
     Put the PR url in the row's Links column, and best-effort mirror it to Plane:
       bash "${PM_CMD}" comment "<tie>" --body "PR: <url>"
   - gh absent OR push fails → push the branch and hand back the manual compare URL
     for the user to open the PR themselves. NEVER fake a PR.

8. [GATE — TYPED CONFIRM, IRREVERSIBLE] GATED MERGE. Double-gated:
   a) CI green — watch it: `gh pr checks <pr> --watch` (or the manual URL). CI
      red → STOP, report which check failed, and do not merge. The user may
      explicitly WAIVE a non-blocking check; record that they did.
   b) TYPED confirm — ask the user to type the exact word `merge <PB-id>`
      (not just "yes"). Only with BOTH (green/waived AND the typed word):
        gh pr merge <pr> --squash --delete-branch
      then clean up the worktree (git -C <path> worktree remove <wt>).

9. MARK DONE (only AFTER the merge lands).
     bash "${PM_CMD}" move "<tie>" --to done --completed-at <iso8601>
   Set the row Status = done, Done at = HH:MM, % complete = 100, and Time taken =
   (Done at − Started) when both are known. If a habit like "Work the plan" /
   "Deep work" is tracked, mark it on completion only:
     bash "${HABITS_CMD}" mark --habit "<name>" --date ${TODAY}

10. LOOP to the next not-done row in NEXT TASKS. When the handed list is exhausted
    → CASCADE.

CASCADE — at each hand-off a [GATE] (confirm before continuing):
  A — LIST DONE, more day left. There are no more rows in NEXT TASKS but the day
    isn't over. Go to CASCADE B.
  B — PROJECT-DAY EXHAUSTED. Offer to pull more ready tasks for the same project:
      bash "${PM_CMD}" ready --projects <pid>
    Append the chosen rows to "## Work tracker" (one row per task, Status =
    planned), then continue the lifecycle on the first new row.
  C — NEW PROJECT. Offer a project not already worked today. On the user's pick,
    ensure its working location is recorded (step 1), pull its ready tasks, append
    them to the tracker, and continue.

WRITE ONLY THE TRACKER. On every status write, rewrite ONLY the "## Work tracker"
