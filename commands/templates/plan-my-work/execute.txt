
--- INSTRUCTIONS — /plan-my-work, the EXECUTION LOOP (PB-94). You drive ONE Plane issue
through a fixed 5-STAGE pipeline: plan → implement → test → ship → land. This is the
only pbrain command that touches code, branches, PRs, and merges — so be deliberate.
State lives in PLANE ONLY: there is no vault Work tracker, no daily-planning file. You
read issue state with `${PM_CMD} spec "<tie>" --read` and write it back with
`${PM_CMD} move/comment/...`. Never fabricate a PR, a CI result, or a merge.

============================ ENTRY MODE (PB-147) ============================
There are FOUR ways pmw enters this loop. The `mode:` value handed in above tells
you which. CRUCIAL: the EXECUTION LOOP BELOW IS IDENTICAL IN ALL FOUR MODES — the
5 stages, the gates, parking, the SRP triage all behave the same. The modes differ
ONLY in (a) how the issue(s) are SELECTED and (b) how the run is GATED. Do not fork
the stage logic per mode.

  mode 1 — BY ID. target_ref is one issue (target_kind=id). Run PRE-FLIGHT + the 5
    stages on it once. This is the plain `/plan-my-work PB-96` path.
  mode 2 — FIX AN ISSUE. target_ref is a DESCRIPTION (target_kind=desc), not an id.
    Run the FIND-OR-FILE cycle (see "MODE 2" below) to resolve it to ONE issue, then
    run the 5 stages on that issue.
  mode 3 — AUTO-DRIVE THE QUEUE. No target. Run the MODE 3 LOOP below: claim the top
    of the cross-project queue, run the 5 stages, park+log at any manual gate, move
    on, repeat until the queue is empty. Hands-off — assume no manual intervention.
  mode 4 — TOP OF QUEUE. The top Queued issue was ALREADY CLAIMED for you (the
    PLAN_MY_WORK_QUEUE_PULL line above names it; target_ref is its tie). Run the 5
    stages on it ONCE, then at CLOSE OFFER to go to the next (do not auto-continue).

A note on selection: modes 3 and 4 consume groom's CROSS-PROJECT ranked queue (the
Queued state, blockers-first), which already EXCLUDES `parked` issues — a human holds
an issue by adding the `parked` label and hands-off modes never touch it. An explicit
mode-1 id run on a parked issue DOES run (a human named it) — see PARKED WARNING.

PARKED WARNING (mode 1 / any explicit id). When you read `spec --read`, if it reports
`is_parked: true`, say so in ONE line ("PB-X is parked (manual hold) — running it
because you named it directly") and proceed. Never silently run a parked issue, and
never auto-select one (only an explicit id reaches a parked issue).

THE 5 STAGES + THEIR LABELS. Each stage checks the issue's own `auto:<stage>` label
(from the `auto_gates` array in `spec --read`). Present → AUTO-ADVANCE the stage
(announce it in one line, don't wait). Absent → it is a MANUAL [GATE]: stop, get an
explicit yes, and if the user doesn't continue, PARK (step P). The stages:
    1 plan      (auto:plan)      worktree + draft the plan + SAVE it to the issue
    2 implement (auto:implement) write the code + commit locally
    3 test      (auto:test)      run the repo's tests / linters, capture results
    4 ship      (auto:ship)      push the branch + open the PR
    5 land      (auto:land)      update docs/etc, then merge (NO new release)
SEMANTICS — INDEPENDENT, STOP-AT-FIRST-GAP: each label clears ONLY its own stage, and
a later label does NOT imply an earlier one. Walk the stages in order; the first stage
whose label is absent is a manual gate — if you don't get the go, PARK there. An issue
with no auto:* labels is fully manual (every stage gated), which is the safe default.
You only READ these labels — never add an auto:* label mid-run to skip your own gate.
INVARIANT — the merge is irreversible and stays SAFE even with auto:land: auto:land
waives ONLY the typed-confirm half of stage 5. A red/failing CI HARD-STOPS the merge
regardless of any label. And land NEVER cuts a release.

YOU WERE HANDED (in the output above):
  • target_ref = ${TARGET_REF} — the issue to run. target_kind = ${TARGET_KIND}:
      - id   → a Plane id (pb96 / PB-96 / 96). Resolve it directly.
      - desc → a free-text description, NOT an id. This is MODE 2 (fix an issue). Run
        the FIND-OR-FILE cycle: search Plane (`${PM_CMD} find "<desc>"`); if there's a
        candidate, CONFIRM with the user it's the one they mean before running it; if
        several, ask which; if the user says NONE match (or there are zero), hand it to
        `${PM_CMD} file "<desc>"` — the FULL triage path, which itself checks whether
        the work is a sub-issue of / relates-to / blocked-by an existing task — and on
        the user's yes execute the id it returns. Never invent or substitute a task.
  • WORKING LOCATIONS (above) — plane.json projects[].work: {path,kind,base_branch,
    isolation} per project. May be empty.
  • ${PM_CMD} is the SOLE writer of Plane. ${PLANE_WEB_BASE} is the clickable link base.

SELF-HOST CHECK. If a `SELFHOST_STALE <branch> <state>` line appeared above, the live
pbrain checkout (this command's own code) is not on a clean, up-to-date main. Surface

--ff-only). No line → nothing to do. (This is about the command wrapper; each task's

=========================== MODE 3 — AUTO-DRIVE LOOP =======================
(ONLY when mode: 3. Other modes skip straight to PRE-FLIGHT for their one issue.)
Hands-off: assume NO manual intervention. You drive groom's CROSS-PROJECT ranked
queue one issue at a time until it's empty. The loop:

  1. CLAIM the top of the queue for this session:
       ${PM_CMD} claim-next --session ${PMW_SESSION}
     It returns ONE ready-row (already cross-project, blockers-first, parked-skipped)
     or `null`. `null` → the queue is empty: STOP and give the roll-up (below).
     claim-next atomically moves the issue to Planning, so a parallel auto-drive picks
     a DIFFERENT issue — never collide on the same top.
  2. RUN the full PRE-FLIGHT + 5 STAGES below on the claimed issue's tie, exactly as
     mode 1 would. Announce which PB-id you're driving.
  3. GATES IN AUTO-DRIVE — there is no human to answer a manual gate, so:
       - A stage whose `auto:<stage>` label is PRESENT auto-advances (normal).
       - The first stage whose label is ABSENT is a manual gate you can't satisfy
         hands-off → PARK there (step P: WIP-commit + push + `pbrain park:` comment),
         then LOG a one-line bottleneck note onto the issue
         (`${PM_CMD} comment "<tie>" --body "pbrain auto-drive: parked at <stage> — needs a human; resume with /plan-my-work <PB-id>"`),
         and MOVE ON to step 1 (next claim). Do NOT stop the whole run for one park.
       - THE LAND GATE specifically: groom never grants `auto:land`, so an issue that
         passes plan/implement/test/ship will reach LAND without it. That's expected —
         PARK at land (the PR stays open + linked), log it as a bottleneck, move on.
         NEVER auto-merge in auto-drive. (A red CI also parks, same as always.)
  4. MID-RUN DISCOVERY (a bug/problem you find while executing) → run the SRP TRIAGE
     below. If the new issue BLOCKS finishing the current one, set the current issue
     `blocked_by` it and MOVE ON to the next claim (leave the current parked/blocked);
     if it doesn't block, file it separate and continue the current issue.
  5. Repeat from step 1.
ROLL-UP (when claim-next returns null): one tight summary — issues DONE (merged),
issues PARKED (each with its stage + reason, e.g. "needs manual merge"), issues FILED
mid-run. This is the hands-off run's report.

==================== SRP MID-LOOP TRIAGE (PB-153, all modes) ===============
At ANY point in the loop a discovery surfaces — the USER says something, or YOU find a
problem (a bug, a missing piece, an unrelated cleanup). Do NOT silently fold it into
the current PR. Triage it so every PR stays SINGLE-RESPONSIBILITY:

  - SRP-FIRST — default to filing a SEPARATE issue: `${PM_CMD} file "<the discovery>"`.
    Only FOLD it into the current PR when it is the SAME single responsibility as the
    current task (the same change, same file/feature, same reason). For a TRIVIAL
    scope/wording delta on the current issue, UPDATE the existing issue instead of
    filing.
  - ALWAYS CAPTURE IT — a new issue, or an update to the existing one. Never drop a
    discovery on the floor.
  - CONDITIONAL BLOCKED-BY — if the separate issue must land before the current PR can
    finish, set the current issue blocked_by the new one:
      ${PM_CMD} update --edits '[{"tie":"<current-tie>","field":"relation:blocked_by","value":"<new-tie>"}]'
    Otherwise just relate them:
      ${PM_CMD} update --edits '[{"tie":"<current-tie>","field":"relation:relates_to","value":"<new-tie>"}]'
  - KEEP PRs SCOPED TO ONE THING. If mid-work you realize the current issue actually
    bundles several PR-worthy tasks, file the distinct ones as separate issues (so each
    gets its own branch/PR) rather than growing one sprawling PR.

================================ PRE-FLIGHT =================================
Resolve target_ref → a single tie (id: direct; desc: find-or-file above). Then read
its state ONCE and branch on dependencies BEFORE touching any stage:

  bash ${PM_CMD} spec "<tie>" --read     # JSON: auto_gates, approved, has_plan, is_parked,
                                         # description, comments, status, blocked_by

  is_parked → see PARKED WARNING above: if true and this was an explicit id (mode 1),
  note it in one line and proceed; you will never reach here with a parked issue from a
  hands-off mode (the queue excludes them).

A) BLOCKED? If `blocked_by` is non-empty, this issue cannot run yet — its open
   blockers must land first. State it in one line, then drive EACH blocker through the
   FULL loop below first (iteration 1…N, in the order given), and only AFTER the last
   blocker merges, come back and run THIS issue (final iteration). If a blocker can't
   be finished (user stops, or it itself parks), STOP and leave this issue blocked —
   do not force it. (On the groom path the ordered stream already put blockers first,
   so `blocked_by` is normally empty here; this is the safety net for a manual run.)

B) PARENT WITH SUB-ISSUES? Check `bash ${PM_CMD} subtree "<tie>"`. If
   `has_open_children` is true, the parent is ONE logical target executed as SEPARATE
   SEQUENTIAL UNITS: drive EACH child in `children` (already sorted priority→due→id)
   through the full loop below, one branch/PR/merge per child, in order. Close the
   PARENT only after the last child merges (PARENT-CLOSE, below). A childless issue (or
   a parent whose children all landed) is driven as a single unit.

C) RESUMING? If the issue's comments carry a `pbrain park:` breadcrumb (branch +
   parked-stage), this is a resume — see stage 1 RE-ATTACH, then jump to the parked
   stage (skip the stages already done).

Once dependencies are clear, run the 5 stages for the (leaf) issue.

============================== THE 5 STAGES ================================
Across all stages: keep the issue a LIVE, SUMMARIZED EXECUTION LOG — at each stage
append a tight comment via `${PM_CMD} comment "<tie>" --body "..."` capturing what
happened + the artifacts (plan link, files changed, TEST RESULTS, PR url, park note).
At the very start, mark it in-progress: `${PM_CMD} move "<tie>" --to doing`.

PB-130 — PIPELINE STATE PER STAGE. On projects bootstrapped with pbrain's custom
state model (Backlog → Todo → Planning → Building → Testing → Shipped + Landed +
Cancelled), advance the issue into the STAGE's state as you ENTER each stage, with
`--to-state`: plan → Planning, implement → Building, test → Testing, ship & land →
Shipped, then Landed on merge (stage 6). The form is
`${PM_CMD} move "<tie>" --to doing --to-state <PipelineState>` (the `--to doing`
keeps the started-group status; `--to-state` picks the named state inside it). On a
project WITHOUT the pipeline states, `--to-state` degrades to the started group's
default — harmless — so always pass it; you don't need to detect the state model.

0. RESOLVE WORKING LOCATION. Look up the issue's project in WORKING LOCATIONS.
   Absent → [GATE] ask the user for the absolute path to the project's repo / workspace
   and offer to record it: `${PM_CMD} workdir "<project-ref>" --path "<abs>"
   [--kind conductor|repo] [--base-branch <b>]`. Verify the path is a git repo.

1. PLAN  (auto:plan)
   ISOLATE — branch off a FRESH base, never a stale HEAD:
     git -C <path> fetch origin
     git -C <path> worktree add <wt> -b pbrain/<short-slug> origin/<base_branch>
   (isolation=branch → `git -C <path> switch -c pbrain/<slug> origin/<base>` instead).
   RE-ATTACH (resume) — if a park breadcrumb named a pushed `pbrain/<slug>` branch, do
   NOT make a fresh empty branch (that orphans the partial work). Re-attach:
     git -C <path> fetch origin
     git -C <path> worktree add <wt> pbrain/<slug>                # local branch exists
   or recreate from the pushed branch if the local one is gone:
     git -C <path> worktree add <wt> -b pbrain/<slug> origin/pbrain/<slug>
   READ the TARGET repo's CLAUDE.md / AGENTS.md conventions (not pbrain's). State the
   branch + base. Move the issue into the Planning state:
     ${PM_CMD} move "<tie>" --to doing --to-state Planning
   THEN the plan itself:
     - approved == true (the issue already has an approved `## Implementation Plan` in
       its description) → FAST PATH: read that plan and implement against it; do not
       re-draft. Honor authoritative user comments if they override the description.
     - approved == false → draft a tight implementation plan against the target repo's
       conventions, and SAVE it to the issue so any later session (or a resume) can read
       it — append a `## Implementation Plan` section to the issue's description:
         ${PM_CMD} update --edits '[{"tie":"<tie>","field":"description","value":"<full existing description_html + the new ## Implementation Plan section>"}]'
       (re-send the FULL existing description_html with the plan appended, so nothing is
       clobbered). Offer once to approve it (`${PM_CMD} spec "<tie>"` → adds
       plan-approved) so future runs fast-path.
   GATE: auto:plan present → announce + proceed. Absent → [GATE] explicit yes before
   writing ANY code; no go → PARK (step P).

2. IMPLEMENT  (auto:implement)
   Move the issue into the Building state: `${PM_CMD} move "<tie>" --to doing --to-state Building`.
   Write code per the plan + the target repo's conventions. Commit locally in the
   worktree (clear message; reference the PB-id). Comment the issue with a one-line
   summary + files changed. GATE: auto:implement → announce + proceed; absent → [GATE];
   no go → PARK.

3. TEST  (auto:test)
   Move the issue into the Testing state: `${PM_CMD} move "<tie>" --to doing --to-state Testing`.
   Run the repo's tests / linters / build. Capture the RESULTS (pass/fail counts, any
   failures) and comment them onto the issue — this is the part a CEO reviews. If tests
   fail, fix and re-run until green (or surface the failure and stop). GATE: auto:test →
   announce + proceed; absent → [GATE]; no go → PARK.

4. SHIP  (auto:ship)
   Move the issue into the Shipped state: `${PM_CMD} move "<tie>" --to doing --to-state Shipped`.
   Probe `command -v gh`.
     - gh present → push the branch, then `gh pr create --fill --base <base_branch>`.
       Put the PR url in the issue: `${PM_CMD} comment "<tie>" --body "PR: <url>"`.
     - gh absent / push fails → push the branch and hand back the manual compare URL for
       the user to open the PR. NEVER fake a PR.
   GATE: auto:ship → announce + proceed; absent → [GATE]; no go → PARK.

5. LAND  (auto:land) — IRREVERSIBLE
   First update docs / changelog / any release-adjacent files the change needs (NO new
   release — never cut or tag a release here). Commit + push those. Then the merge,
   DOUBLE-gated:
     a) CI green — watch it: `gh pr checks <pr> --watch` (or the manual URL). CI red →
        STOP, report which check failed, do not merge. INVARIANT: auto:land NEVER
        waives this — a red CI hard-stops regardless of the label. (No CI configured in
        the repo = nothing to wait on; say so.)
     b) Typed confirm — ask the user to type the exact word `land <PB-id>` (or
        `merge <PB-id>`). PB-94: auto:land waives THIS half only — announce
        "auto:land — merging on green" and proceed once (a) is green. Without auto:land,
        the typed word is required.
   With BOTH satisfied (green/waived AND [typed word OR auto:land]):
     gh pr merge <pr> --squash --delete-branch
   then clean up with the GC sweep (squash-merge safe; removes this now-merged worktree
   + its pbrain/<slug> branch, and harmlessly SKIPS any not-yet-merged/dirty peers):
     ${PM_CMD} prune-merged --repo <path>
   GATE: auto:land present → (typed half waived, CI still required); absent → manual
   typed-confirm gate; no go → PARK (the PR stays open; resume re-attaches at this
   stage).

6. MARK DONE (only AFTER the merge lands).
     ${PM_CMD} move "<tie>" --to done --completed-at <iso8601>
   Comment a final one-line summary (merged commit / PR). If a tracked habit applies and
   ${HABITS_CMD} is available, mark it.

PARENT-CLOSE (only when a parent target's LAST open child has merged — re-check
`${PM_CMD} subtree "<parent-ref>"` reports has_open_children=false):
     ${PM_CMD} move "<parent-tie>" --to done --completed-at <iso8601>
   If ANY child is still unfinished (a child parked / user stopped), leave the parent
   OPEN — never force-close it.

============================ P. PARK (resumable) ==========================
You PARK when you hit a manual stage you won't advance in this run (no go, or the user
stops). Parking must leave the partial work DURABLE + RESUMABLE:
  - Parked before isolate (no worktree yet) → nothing on disk; just leave the doing
    status. Resume starts fresh.
  - Parked with a WORKTREE but NO PR yet (plan / implement / test) → the work is local
    and would be lost. Make it durable BEFORE parking:
        git -C <wt> add -A
        git -C <wt> commit -m "WIP: <PB-id> parked at <stage> (pbrain auto-exec)"   # ok if nothing to commit
        git -C <wt> push -u origin pbrain/<slug>
  - Parked after the PR opened (ship / land) → already durable (pushed + PR link in the
    issue). No extra commit.
THEN record the resume breadcrumb on the issue (this is the resume key):
     ${PM_CMD} comment "<tie>" --body "pbrain park: branch pbrain/<slug>, parked at <stage>; <PR url if any>; resume with /plan-my-work <PB-id>"
   Leave the status as doing. Never `worktree remove` a parked worktree — only a
   successful merge (stage 5) removes it, via `${PM_CMD} prune-merged` whose merged+clean
   gate inherently skips a parked worktree (it is either unmerged or carries a WIP commit
   that diverges from base → KEPT). A different machine can still resume from the pushed
   branch (stage 1 RE-ATTACH recreates the worktree from origin/pbrain/<slug>).

================================== CLOSE ==================================
When the issue (or, for a parent, its last child) is done — or you parked — give one
tight summary: which stages auto-advanced, where it parked (and the manual stage), and
the branch/PR. Then close per MODE:
  - mode 1 / 2 — you drove ONE issue; do NOT pick up another. Stop here.
  - mode 4 (top of queue) — OFFER to go to the next: "Want me to take the next queue
    item? (`/plan-my-work` / `/plan-my-work next`)". Do NOT auto-continue — wait for
    the user. This is the manual gate between queue items.
  - mode 3 (auto-drive) — you do NOT stop on one issue: loop back to MODE 3 step 1
    (claim the next). Only when claim-next returns null do you emit the ROLL-UP and
    stop. (Selection + ranking is groom's job; you only consume the queue.)
