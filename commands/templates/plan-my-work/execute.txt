
--- INSTRUCTIONS — /plan-my-work, the EXECUTION LOOP (PB-94). You drive ONE Plane issue
through a fixed 5-STAGE pipeline: plan → implement → test → ship → land. This is the
only pbrain command that touches code, branches, PRs, and merges — so be deliberate.
State lives in PLANE ONLY: there is no vault Work tracker, no daily-planning file. You
read issue state with `${PM_CMD} spec "<tie>" --read` and write it back with
`${PM_CMD} move/comment/...`. Never fabricate a PR, a CI result, or a merge.

THE 5 STAGES + THEIR LABELS. Each stage checks the issue's own `auto:<stage>` label
(from the `auto_gates` array in `spec --read`). Present → AUTO-ADVANCE the stage
(announce it in one line, don't wait). Absent → it is a MANUAL [GATE]: stop, get an
explicit yes, and if the user doesn't continue, PARK (step P). The stages:
    1 plan      (auto:plan)      worktree + draft the plan + SAVE it to the issue
    2 implement (auto:implement) write the code + commit locally
    3 test      (auto:test)      run the repo's tests / linters, capture results
    4 ship      (auto:ship)      push the branch + open the PR
    5 land      (auto:land)      update docs/etc, then merge (NO new release)
SEMANTICS — INDEPENDENT, STOP-AT-FIRST-GAP: each label clears ONLY its own stage, and
a later label does NOT imply an earlier one. Walk the stages in order; the first stage
whose label is absent is a manual gate — if you don't get the go, PARK there. An issue
with no auto:* labels is fully manual (every stage gated), which is the safe default.
You only READ these labels — never add an auto:* label mid-run to skip your own gate.
INVARIANT — the merge is irreversible and stays SAFE even with auto:land: auto:land
waives ONLY the typed-confirm half of stage 5. A red/failing CI HARD-STOPS the merge
regardless of any label. And land NEVER cuts a release.

  • WORKING LOCATIONS (above) — plane.json projects[].work: {path,kind,base_branch,

  • ${PM_CMD} is the SOLE writer of Plane. ${PLANE_WEB_BASE} is the clickable link base.

A) BLOCKED? If `blocked_by` is non-empty, this issue cannot run yet — its open

C) RESUMING? If the issue's comments carry a `pbrain park:` breadcrumb (branch +

Once dependencies are clear, run the 5 stages for the (leaf) issue.

============================== THE 5 STAGES ================================
Across all stages: keep the issue a LIVE, SUMMARIZED EXECUTION LOG — at each stage
append a tight comment via `${PM_CMD} comment "<tie>" --body "..."` capturing what
happened + the artifacts (plan link, files changed, TEST RESULTS, PR url, park note).
At the very start, mark it in-progress: `${PM_CMD} move "<tie>" --to doing`.

0. RESOLVE WORKING LOCATION. Look up the issue's project in WORKING LOCATIONS.
   Absent → [GATE] ask the user for the absolute path to the project's repo / workspace
   and offer to record it: `${PM_CMD} workdir "<project-ref>" --path "<abs>"
   [--kind conductor|repo] [--base-branch <b>]`. Verify the path is a git repo.

1. PLAN  (auto:plan)
   ISOLATE — branch off a FRESH base, never a stale HEAD:
     git -C <path> fetch origin
     git -C <path> worktree add <wt> -b pbrain/<short-slug> origin/<base_branch>
   (isolation=branch → `git -C <path> switch -c pbrain/<slug> origin/<base>` instead).
   RE-ATTACH (resume) — if a park breadcrumb named a pushed `pbrain/<slug>` branch, do
   NOT make a fresh empty branch (that orphans the partial work). Re-attach:
     git -C <path> fetch origin
     git -C <path> worktree add <wt> pbrain/<slug>                # local branch exists
   or recreate from the pushed branch if the local one is gone:
     git -C <path> worktree add <wt> -b pbrain/<slug> origin/pbrain/<slug>
   READ the TARGET repo's CLAUDE.md / AGENTS.md conventions (not pbrain's). State the
   branch + base. THEN the plan itself:
     - approved == true (the issue already has an approved `## Implementation Plan` in
       its description) → FAST PATH: read that plan and implement against it; do not
       re-draft. Honor authoritative user comments if they override the description.
     - approved == false → draft a tight implementation plan against the target repo's
       conventions, and SAVE it to the issue so any later session (or a resume) can read
       it — append a `## Implementation Plan` section to the issue's description:
         ${PM_CMD} update --edits '[{"tie":"<tie>","field":"description","value":"<full existing description_html + the new ## Implementation Plan section>"}]'
       (re-send the FULL existing description_html with the plan appended, so nothing is
       clobbered). Offer once to approve it (`${PM_CMD} spec "<tie>"` → adds
       plan-approved) so future runs fast-path.
   GATE: auto:plan present → announce + proceed. Absent → [GATE] explicit yes before
   writing ANY code; no go → PARK (step P).

2. IMPLEMENT  (auto:implement)
   Write code per the plan + the target repo's conventions. Commit locally in the
   worktree (clear message; reference the PB-id). Comment the issue with a one-line
   summary + files changed. GATE: auto:implement → announce + proceed; absent → [GATE];
   no go → PARK.

3. TEST  (auto:test)
   Run the repo's tests / linters / build. Capture the RESULTS (pass/fail counts, any
   failures) and comment them onto the issue — this is the part a CEO reviews. If tests
   fail, fix and re-run until green (or surface the failure and stop). GATE: auto:test →
   announce + proceed; absent → [GATE]; no go → PARK.

4. SHIP  (auto:ship)
   Probe `command -v gh`.
     - gh present → push the branch, then `gh pr create --fill --base <base_branch>`.
       Put the PR url in the issue: `${PM_CMD} comment "<tie>" --body "PR: <url>"`.
     - gh absent / push fails → push the branch and hand back the manual compare URL for
       the user to open the PR. NEVER fake a PR.
   GATE: auto:ship → announce + proceed; absent → [GATE]; no go → PARK.

5. LAND  (auto:land) — IRREVERSIBLE
   First update docs / changelog / any release-adjacent files the change needs (NO new
   release — never cut or tag a release here). Commit + push those. Then the merge,
   DOUBLE-gated:
     a) CI green — watch it: `gh pr checks <pr> --watch` (or the manual URL). CI red →
        STOP, report which check failed, do not merge. INVARIANT: auto:land NEVER
        waives this — a red CI hard-stops regardless of the label. (No CI configured in
        the repo = nothing to wait on; say so.)
     b) Typed confirm — ask the user to type the exact word `land <PB-id>` (or
        `merge <PB-id>`). PB-94: auto:land waives THIS half only — announce
        "auto:land — merging on green" and proceed once (a) is green. Without auto:land,
        the typed word is required.
   With BOTH satisfied (green/waived AND [typed word OR auto:land]):
     gh pr merge <pr> --squash --delete-branch
   then clean up: git -C <path> worktree remove <wt>.
   GATE: auto:land present → (typed half waived, CI still required); absent → manual
   typed-confirm gate; no go → PARK (the PR stays open; resume re-attaches at this
   stage).

6. MARK DONE (only AFTER the merge lands).
     ${PM_CMD} move "<tie>" --to done --completed-at <iso8601>
   Comment a final one-line summary (merged commit / PR). If a tracked habit applies and
   ${HABITS_CMD} is available, mark it.

PARENT-CLOSE (only when a parent target's LAST open child has merged — re-check
`${PM_CMD} subtree "<parent-ref>"` reports has_open_children=false):
     ${PM_CMD} move "<parent-tie>" --to done --completed-at <iso8601>
   If ANY child is still unfinished (a child parked / user stopped), leave the parent
   OPEN — never force-close it.

============================ P. PARK (resumable) ==========================
You PARK when you hit a manual stage you won't advance in this run (no go, or the user
stops). Parking must leave the partial work DURABLE + RESUMABLE:
  - Parked before isolate (no worktree yet) → nothing on disk; just leave the doing
    status. Resume starts fresh.
  - Parked with a WORKTREE but NO PR yet (plan / implement / test) → the work is local
    and would be lost. Make it durable BEFORE parking:
        git -C <wt> add -A
        git -C <wt> commit -m "WIP: <PB-id> parked at <stage> (pbrain auto-exec)"   # ok if nothing to commit
        git -C <wt> push -u origin pbrain/<slug>
  - Parked after the PR opened (ship / land) → already durable (pushed + PR link in the
    issue). No extra commit.
THEN record the resume breadcrumb on the issue (this is the resume key):
     ${PM_CMD} comment "<tie>" --body "pbrain park: branch pbrain/<slug>, parked at <stage>; <PR url if any>; resume with /plan-my-work <PB-id>"
   Leave the status as doing. Never `worktree remove` a parked worktree — only a
   successful merge (stage 5) removes it. A different machine can still resume from the
   pushed branch (stage 1 RE-ATTACH recreates the worktree from origin/pbrain/<slug>).
